# Feature Specification: 营销 C 端（批次09）

**Feature Branch**: `015-marketing-c`

**Created**: 2026-09-22

**Status**: Draft

**Input**: 批次 09：营销 C 端。**12 个 shop 端点**（当前全为 `CodeNotImplemented` 桩，且**C 端 service 接口整体缺失**——需按批次 03 的 `IOperationLogic` 先例新建）：5 类活动**公开列表**（拼团/秒杀/砍价/助力/满减）、**砍价 3 动作**（发起/进度/帮砍）、**助力 3 动作**（发起/进度/助力）、**首页聚合**（`/index` 现为占位契约）。本批**同时清偿批次 07 记下的秒杀欠账**（该批已把秒杀下单临时拦为"未上线"）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 秒杀可见且可下单（Priority: P1）🎯 MVP

买家在秒杀列表看到进行中与预告的场次（含秒杀价、活动剩余量、每人限购）；选一场次商品发起下单时，**按秒杀价成交**，且活动库存独立扣减（与商品库存不混淆）；订单取消时活动库存回补。

**Why this priority**: 秒杀是交易链路里**唯一被显式截断**的玩法——批次 07 因"价格未接/库存不锁/取消不回补"而把秒杀下单**临时拒绝**（`FlashSaleItemId>0 → 50002`），该欠账已记账并指定由本批清偿。不通，则"四玩法下单"始终缺一条腿。

**Independent Test**: 造进行中的秒杀场次（含场次商品）→ 列表可见 → 用该场次商品下单 → 订单项成交价为**秒杀价**（快照）、活动 `sold_count` 增加 → 取消该单 → `sold_count` 回补。

**Acceptance Scenarios**:

1. **Given** 一个进行中的秒杀场次（商品 A 秒杀价 5.00、原价 10.00、限量 10），**When** 查询秒杀列表，**Then** 返回该场次且含秒杀价/剩余量/限购数。
2. **Given** 上述场次，**When** 买家下单 2 件，**Then** 订单项 `price` 与 `original_price` 分别记录**秒杀价**与**原价**，订单应付按秒杀价计；活动 `sold_count +2`。
3. **Given** 上述场次剩余量仅 1，**When** 下单 2 件，**Then** 拒绝（活动库存不足），不落单。
4. **Given** 一笔秒杀订单处于待付款，**When** 买家取消，**Then** 活动库存回补（`sold_count -数量`）。
5. **Given** 场次商品与所选 SKU 不一致（篡改请求），**When** 下单，**Then** 拒绝（场次商品校验）。
6. **Given** 秒杀活动已结束，**When** 列表查询，**Then** 不出现在"进行中"；已结束场次不可下单。

### User Story 2 - 砍价（Priority: P1）

买家从砍价活动列表选一个场次商品**发起砍价**（发起即砍第一刀），随后把砍价单分享给好友，好友可**一人一刀**帮砍；砍到**底价**后可按底价下单。砍价单有时效，超时即失效。帮砍入口必须防刷。

**Why this priority**: 砍价的"发起—帮砍—到底价—下单"是本批最完整的玩法闭环，且帮砍是社交裂变的核心动作。

**Independent Test**: 发起砍价 → 返回砍价单号与首刀后价格 → 另一会员帮砍一刀 → 进度可见、当前价下降 → 砍到底价 → 状态变为"到底价"（可下单）→ 同一人再砍 → 被拒（一人一刀）。

**Acceptance Scenarios**:

1. **Given** 场次商品（原价 100.00、底价 60.00、最多 5 刀），**When** 买家发起砍价，**Then** 创建砍价单（砍价中）、当前价为首刀后的价格（起始价 − 每刀金额）。
2. **Given** 进行中的砍价单，**When** 另一会员帮砍一刀，**Then** 当前价下降一档、帮砍列表增加该人（昵称脱敏）。
3. **Given** 同一会员已帮砍过该单，**When** 再次帮砍，**Then** 拒绝（一人一刀）。
4. **Given** 发起者本人，**When** 帮砍自己的单，**Then** 拒绝。
5. **Given** 当前价已到下（或本该到但会被砍穿），**When** 再帮砍，**Then** 不砍穿（当前价不低于底价），状态变为"到底价"。
6. **Given** 已超时的砍价单，**When** 帮砍或查询后变更，**Then** 状态为"超时"且不可再砍。
7. **Given** 已被风控拦截的会员，**When** 帮砍，**Then** 拒绝（防刷）。

### User Story 3 - 助力（Priority: P2）

买家从助力活动列表选一个活动**发起助力**（发起后生成参与记录），把记录分享给好友；好友可**一人一次**助力，达到活动要求的人数后视为完成并**发奖**。发起次数受活动限制。

**Why this priority**: 与砍价同族的裂变玩法，机制更简单（只数人数、不涉及价格），故 P2 但同批交付。

**Independent Test**: 发起助力（要求 3 人）→ 两个好友各助力一次 → 进度 2/3 未完成 → 第三人助力 → 达标、状态"已完成发奖" → 同一人重复助力被拒。

**Acceptance Scenarios**:

1. **Given** 进行中的助力活动（需 3 人、每人限发起 1 次），**When** 会员发起，**Then** 返回参与记录号，进度 0/3。
2. **Given** 上述记录，**When** 三位不同好友各助力一次，**Then** 前三位的助力计入进度、第三位后状态变为"已完成发奖"，并**投递发奖意图**（奖励类型 1 券 / 2 积分）。
3. **Given** 同一好友重复助力，**When** 再次助力，**Then** 拒绝（一人一助力）。
4. **Given** 发起者本人，**When** 助力自己的记录，**Then** 拒绝。
5. **Given** 该会员已达"每人可发起次数"上限，**When** 再次发起，**Then** 拒绝。
6. **Given** 活动已结束/未开始，**When** 发起，**Then** 拒绝。

### User Story 4 - 活动列表与首页聚合（Priority: P2）

买家可从首页一次拿到：轮播、楼层、**五类活动入口**（秒杀/拼团/砍价/助力/满减各自的进行中活动）与**可领优惠券**。同时五类活动也各有独立的公开列表接口（供活动页使用）。

**Why this priority**: 这是"发现入口"，把前三个故事的能力暴露给用户；不改变玩法机制。

**Independent Test**: 造进行中的五类活动各一个 + 在投轮播 + 启用楼层 + 可领券 → 请求首页 → 一次返回轮播、楼层、5 个活动入口、券列表；五类列表接口各自只返回进行中的活动。

**Acceptance Scenarios**:

1. **Given** 五类活动各有一个进行中、另有各一个已结束，**When** 请求首页，**Then** 活动入口只含进行中的，且各入口数量不超过约定上限。
2. **Given** 首页有轮播与楼层配置，**When** 请求首页，**Then** 两者按既有投放/排序口径返回（复用批次 03 的能力）。
3. **Given** 存在可领券，**When** 请求首页，**Then** 返回券列表（口径与既有"可领券列表"一致）。
4. **Given** 各活动列表接口，**When** 分页请求，**Then** 只返回进行中（秒杀含预告）、按活动结束时间排序。

---

### Edge Cases

- **秒杀库存双账**：活动库存（`flash_sale_item.sold_count` vs `stock_count`）与商品库存（`inventory`）必须**各自独立且都正确**：下单需同时锁定两者，任一无货即拒绝；支付成功核销商品库存；取消回补两者。（批次 07 的教训：只锁活动库存会导致支付回调核销失败 → 订单永远无法支付。）
- **秒杀价快照**：订单项必须记录**成交价（秒杀价）**与**原价**，售后/对账以成交价为准。
- **一人一刀/一人一助力**：靠"只追加的帮砍/助力记录表 + 唯一约束或条件写入"保证；并发重复点击只能成功一次。
- **砍价不砍穿**：当前价不得低于底价；最后一刀补齐到"恰好底价"（避免多砍出负数）。
- **助力达标并发**：多人同时助力时，"达标"只能触发**一次**发奖意图。
- **风控挂载**：帮砍/助力入口必须挂风控（迁移 000029 明写"被刷重灾区"）；本批通过端口调用，未装配时降级放行并告警（与既有端口约定一致）。
- **发奖口径**：奖励类型 1 券 / 2 积分，其**实际发放跨域**（user 域）——本批只投递发奖意图（端口），实际发放随装配/后续批次接（用户裁定）。
- **首页无可用内容**：任一分块为空时返回空数组而非报错（首页可用性优先）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 秒杀公开列表必须返回"进行中 + 预告"的场次，含场次商品的秒杀价、活动剩余量、每人限购。
- **FR-002**: 秒杀下单必须**按秒杀价成交**并把秒杀价/原价快照进订单项；必须校验"所购 SKU 属于该场次商品"。
- **FR-003**: 秒杀下单必须**同时**做活动库存（`stock_count - sold_count >= 数量` 的条件更新）与商品库存锁定；任一不足即拒绝且不落单。
- **FR-004**: 秒杀订单取消必须回补活动库存（`sold_count - 数量`）与商品库存锁定；已结束/超量的场次不得下单。
- **FR-005**: 本批必须**解除批次 07 对秒杀下单的临时拦截**（该闸的删除条件即 FR-002~004 落地）。
- **FR-006**: 砍价公开列表必须返回进行中的砍价活动（含场次商品的起始价/底价/最大刀数）。
- **FR-007**: 会员必须能对**场次商品**发起砍价：创建砍价单、发起即砍第一刀、设定有效期；同一会员对同一场次商品可发起的次数受活动限制。
- **FR-008**: 砍价单必须可公开查询进度：当前价、底价、已砍刀数、状态、有效期、帮砍列表（昵称脱敏）。
- **FR-009**: 会员必须能帮砍（**一人一刀**，发起者本人不可帮砍自己）；每刀金额按"（起始价−底价）÷ 最大刀数"计算，**最后一刀补齐到恰好底价**（不砍穿、不低于底价）。
- **FR-010**: 砍价当前价到达底价时，状态必须变为"到底价"（可下单）；超时未砍到底价的单必须判定为"超时"且不可再砍。
- **FR-011**: 助力公开列表必须返回进行中的助力活动（含所需人数、每人可发起次数、奖励类型）。
- **FR-012**: 会员必须能发起助力：创建参与记录；受"每人可发起次数"与活动时间窗限制。
- **FR-013**: 会员必须能助力他人记录（**一人一助力**，发起者本人不可助力自己）；达成所需人数时置"已完成发奖"并**投递发奖意图**（奖励类型 1 券/2 积分，实际发放跨域，见 Assumptions）。
- **FR-014**: 助力达标在并发下只允许**一次**发奖意图（不得重复发奖）。
- **FR-015**: 帮砍与助力入口必须挂**风控**（迁移 000029 明确要求）；风控未装配时降级放行并告警（端口约定）。
- **FR-016**: 满减公开列表必须返回进行中的满减活动（含档位与适用范围摘要）。
- **FR-017**: 首页聚合必须一次返回：轮播、楼层、五类活动入口（各取进行中的若干条）、可领券列表；任一分块为空时返回空数组而非报错。
- **FR-018**: 全部列表必须分页且只返回"有效"活动（启用、未删除、在时间窗内），排序口径在各列表与首页入口之间保持一致。
- **FR-019**: 本批 12 个端点必须由 `CodeNotImplemented` 桩变为可用实现（SC-001 的数字化依据）。

### Key Entities *(include if feature involves data)*

- **秒杀（flash_sale_activity / flash_sale_item）**：场次（起止时间）与场次商品（秒杀价、限量 `stock_count`、已售 `sold_count`、每人限购）。活动库存独立于商品库存。
- **拼团（group_buy_activity / group_buy_item / group_buy_team / group_buy_team_member）**：成团价与人数字段（本批只做**列表**，成团/解散属批次 10/11 的结算面）。
- **砍价（bargain_activity / bargain_item / bargain_record / bargain_helper）**：场次商品（起始价/底价/最大刀数/配置）与砍价单（当前价/刀数/状态/有效期/成交单号）+ 只追加的帮砍记录。
- **助力（assist_activity / assist_record / assist_helper）**：活动（所需人数/每人限发起/奖励类型与载体）与参与记录（助力人数/状态/完成时间）+ 只追加的助力记录。
- **满减（promotion_activity / promotion_activity_ladder / promotion_activity_scope）**：档位与适用范围（结算侧已由批次 06 消费）。
- **首页装配**：轮播/楼层（既有装修域）、五类活动入口、可领券——只读聚合，不新增存储。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本批 12 个端点全部脱离"未实现"状态（shop 桩数 12→0）。
- **SC-002**: 秒杀闭环可演示：列表 → 秒杀价下单 → 活动/商品库存双扣 → 取消双回补；且**支付回调不再因库存核销失败而回滚**（批次 07 的欠账清偿）。
- **SC-003**: 砍价闭环可演示：发起 → 他人帮砍 → 到底价 → 状态可下单；"一人一刀""不砍穿""超时失效"在重复与并发下 100% 成立。
- **SC-004**: 助力闭环可演示：发起 → 一人一助力 → 达标发奖意图仅投递一次；"一人一助力""发起次数上限"在并发下成立。
- **SC-005**: 首页一次请求返回轮播/楼层/活动入口/券四类内容，任一为空不影响整体可用。

## Assumptions

- **发奖跨域（用户裁定）**：助力的实际发放（发券/发积分）依赖 user 域；本批只按"端口投递意图"落地（同批次 07 的 `ICommissionReverse` 形态），实际发放与装配随后续批次接。
- **风控（端口）**：`IRiskLogic` 的实现属批次 12；本批在帮砍/助力入口通过端口调用，未装配时降级放行并告警（不阻塞玩法可用）。
- **拼团只做列表**：本批不含成团/解散/退款的结算面（属批次 10/11）；拼团下单沿用既有的 `GroupBuyTeamId` 上下文（批次 06 已透传）。
- **砍价金额算法**：每刀金额 =（起始价 − 底价）÷ 最大刀数（向下取整到分），最后一刀补齐到恰好底价——**确定性算法**（便于测试与用户可预期），不使用随机金额。
- **砍价有效期**：以砍价单落库的到期时间为准（由活动配置或统一默认时长决定）。
- **首页入口数量**：每类活动入口取**固定条数上限**（进行中按结束时间升序取前 N）。
- **秒杀"商品库存"与"活动库存"都要锁**：这是批次 07 记录的必要条件（只锁活动库存会让支付回调的库存核销必然失败）。
- **依赖**：批次 06（订单/支付链路与 `FlashSaleItemId`/`GroupBuyTeamId` 透传）、批次 03（装修域 PublicBanners/PublicFloors）、批次 06 的券域 `PublicList`。
- **表**：五类玩法的表与索引均已存在（V17/V18/V20/V29），本批**预期零迁移**；若发现列缺失按协议记账后补。
