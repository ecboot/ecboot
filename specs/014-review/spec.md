# Feature Specification: 评价域（批次08）

**Feature Branch**: `014-review`

**Created**: 2026-09-22

**Status**: Draft

**Input**: 批次 08：评价域（014-review）。4 个 C 端端点（全部在 shop 渠道，当前均为 `CodeNotImplemented` 桩）：提交评价 / 追评 / 我的评价 / 商品评价列表；接口 `IReviewLogic` 已有 Create/Extra/MyList 三方法与规则注释，第 4 个端点缺方法（按先例微扩）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 会员提交评价（Priority: P1）🎯 MVP

买家在订单完成后，对**已完成的订单项**发表评价：打 1–5 星、写评价内容、可选上传图片、可选匿名。系统必须保证"**一项一评**"（同一订单项只能评一次，重复提交被拒），且新评价的初始状态为**通过**（V1 自动通过, 用户裁定 B——理由与合规债务见 Edge Cases/Assumptions）。

**Why this priority**: 评价的写入入口是整条评价链路的第一环；没有它，列表与汇总都无数据。

**Independent Test**: 造一笔已完成订单的订单项 → 提交评价 → 返回评价 ID 且初始状态为"通过"；对同一订单项再次提交 → 被拒（已评价）。

**Acceptance Scenarios**:

1. **Given** 本人已完成订单的订单项（未评过），**When** 提交 5 星评价，**Then** 创建评价（V1 初始状态=通过）并返回评价 ID。
2. **Given** 该订单项已有评价，**When** 再次提交，**Then** 拒绝（已评价），不产生第二条。
3. **Given** 他人订单的订单项，**When** 提交评价，**Then** 按"不存在"处理（不泄露他人资源）。
4. **Given** 订单项所属订单**未完成**（如待发货），**When** 提交评价，**Then** 拒绝（仅已完成可评）。
5. **Given** 评分越界（0 或 6），**When** 提交，**Then** 拒绝（参数校验）。

---

### User Story 2 - 商品评价列表与汇总（Priority: P1）

商品详情页展示该商品的评价：**只展示审核通过的评价**，支持按星级筛选与分页，并给出汇总（平均分 + 各星级分布 + 总数）。匿名评价的展示必须隐藏评价人身份。

**Why this priority**: 这是评价功能的**消费端**，也是买家做购买决策的依据。

**Independent Test**: 造若干评价（部分已通过、部分待审/驳回）→ 拉商品评价列表 → 只出现已通过的；按星级筛选生效；汇总与已通过评价一致。

**Acceptance Scenarios**:

1. **Given** 某商品有 2 条已通过、1 条待审、1 条驳回的评价，**When** 查询该商品评价列表（不筛星级），**Then** 只返回 2 条已通过的。
2. **Given** 上述数据，**When** 按 5 星筛选，**Then** 只返回其中 5 星的已通过评价。
2b. **Given** 新提交的评价（V1 自动通过），**When** 查询商品评价列表，**Then** 立即可见（这是 V1 口径的直接后果）。
3. **Given** 上述数据，**When** 查看汇总，**Then** 平均分/分布/总数只统计已通过的评价。
4. **Given** 一条匿名评价，**When** 在列表中展示，**Then** 评价人显示为脱敏标识（不泄露昵称/手机号）。
5. **Given** 评价包含购买规格与商家回复，**When** 展示，**Then** 规格与回复随评价一并返回。

---

### User Story 3 - 我的评价（Priority: P2）

买家可以查看自己发表过的评价列表（分页），每条含商品名、评分、内容、**审核状态**（待审/通过/驳回）、追评内容与商家回复。

**Why this priority**: 让买家知道自己的评价处于什么状态（尤其被驳回时）；不阻塞主链路，故 P2。

**Independent Test**: 造本人 2 条评价（1 通过 1 待审）+ 他人 1 条 → 查询我的评价 → 只返回本人的 2 条且状态正确。

**Acceptance Scenarios**:

1. **Given** 本人有 2 条评价（不同审核状态），**When** 查询我的评价，**Then** 返回 2 条且各自状态正确。
2. **Given** 他人评价存在，**When** 查询我的评价，**Then** 不出现他人的评价。
3. **Given** 评价已有追评与商家回复，**When** 查询我的评价，**Then** 追评与回复一并返回。

---

### User Story 4 - 追加评价（Priority: P2）

买家可以对**已发表的主评价**追加一次追评（补充使用体验），并可选上传图片。追评机会只有一次，且**必须在主评价发表后 90 天内**使用；超期或已追评过一律拒绝。

**Why this priority**: 提升评价信息量，但非关键路径，故 P2。

**Independent Test**: 造一条 30 天前的主评价 → 追评成功且仅一次；再次追评被拒；造一条 100 天前的主评价 → 追评被拒（超期）。

**Acceptance Scenarios**:

1. **Given** 本人 30 天前的主评价未追评，**When** 提交追评，**Then** 成功且追评内容/时间落库。
2. **Given** 已追评过的评价，**When** 再次追评，**Then** 拒绝（限一次）。
3. **Given** 主评价发表已超 90 天，**When** 追评，**Then** 拒绝（超期）。
4. **Given** 他人的评价，**When** 追评，**Then** 按"不存在"处理。

---

### Edge Cases

- **重复提交的并发防护**：同一订单项几乎同时提交两次评价 → 只能成功一次，另一次得到"已评价"业务错误（不得出现两条评价，也不得把数据库唯一键冲突原样抛给用户）。
- **驳回后的展示**：被驳回的评价不出现在商品评价列表与汇总中，但在"我的评价"里可见且状态为"驳回"。
- **匿名评价的边界**：匿名只影响**对外展示**；"我的评价"里本人仍能看到自己的评价内容。
- **空内容评价**：允许仅打分不写内容（`content` 非必填）；但追评内容必填。
- **评价图片**：可选，为空时存空数组而非 NULL。
- **审核入口缺失（已裁定 2026-09-22 用户选择 B：V1 自动通过）**：本批只有 C 端 4 个端点、**没有后台审核端点**（13 批规划内无后台评价管理批）。若严格按既有契约"仅审核通过可见"，商品评价列表将**恒为空**（无人能审核）；故 V1 采取**新评价自动通过（audit_status=1）**，审核字段与 `IReviewLogic.Audit` 能力保留，待后续补后台审核面时切换为"先审后发"。
  ⚠️ **合规债务（记账在案）**：UGC 未经审核即公开，属中国 UGC 平台的内容审核责任缺口——**公开上线前必须补齐审核面**（PROGRESS §五 已记账）。
- **商家回复**：接口存在 `Reply` 方法但无 API 端点（属死契约）→ 本批不实现回复写入，仅透出已存在的回复内容。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 会员必须能对**本人订单中已完成的订单项**提交评价，评分 1–5 星，内容可选，图片可选，可匿名。
- **FR-002**: 系统必须保证"**一项一评**"：同一订单项只能有一条评价；重复提交（含并发）必须被拒绝且不产生第二条。数据库唯一约束为最后防线，冲突须转为业务错误。
- **FR-003**: 新评价的初始审核状态为**通过**（V1 自动通过，用户裁定 B）；审核状态取值 待审/通过/驳回，字段与审核能力保留供后续"先审后发"（见 Assumptions 的合规债务）。
- **FR-004**: 评价必须记录成因快照：订单号、订单项、商品（SPU/SKU）与下单时的规格快照、评价人。
- **FR-005**: 会员必须能查询**自己的**评价列表（分页），含审核状态、追评内容与商家回复；他人评价不可见。
- **FR-006**: 会员必须能对**本人的主评价**追加一次追评（内容必填、图片可选），且仅在主评价发表后 **90 天内**允许；已追评或超期一律拒绝。
- **FR-007**: 商品评价列表必须**只展示审核通过的评价**，支持按星级（1–5）筛选与分页。
- **FR-008**: 商品评价列表必须返回**汇总**：平均分、各星级分布、评价总数——口径与"仅审核通过"一致。
- **FR-009**: 匿名评价在对外展示（商品评价列表）中必须脱敏；非匿名评价按脱敏规则展示评价人标识。
- **FR-010**: 评价列表返回项必须包含：评分、内容、图片、下单规格、追评内容、商家回复、评价时间。
- **FR-011**: 所有写入必须防并发重入（"一项一评"与"追评限一次"两处均须有防线），重复请求不得产生重复数据。
- **FR-012**: 本批 4 个端点必须由 `CodeNotImplemented` 桩变为可用实现（SC-001 的数字化依据）。

### Key Entities *(include if feature involves data)*

- **评价（product_review）**：所属订单项（唯一）、订单号、评价人、SPU/SKU、下单时的商品名与规格快照、评分、内容、图片、是否匿名、审核状态、追评内容与时间、商家回复与时间、创建时间。
- **订单项（trade_order_item）**：提供"是否可评"的依据（所属订单须已完成）与规格快照来源。
- **订单（trade_order）**：提供订单完成状态与订单号。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本批 4 个端点全部脱离"未实现"状态（shop 桩数 16→12）。
- **SC-002**: 评价全链路可演示：提交 → 我的评价可见（含状态）→ 审核通过后出现在商品评价列表与汇总中。
- **SC-003**: "一项一评"在重复与并发提交下 100% 成立（任意构造都不会出现同一订单项两条评价）。
- **SC-004**: 商品评价列表与汇总**只**统计审核通过的评价；匿名评价在对外展示中不泄露身份（既有订单/售后链路回归零退化）。

## Assumptions

- **无后台审核端点**：本批只交付 C 端 4 个端点；`IReviewLogic` 中的 `Reply`/`Audit`/`PendingAudit` 三个方法**没有任何 API 端点**（13 批规划里无后台评价管理批）→ 属**死契约**，本批不动并记账（PROGRESS §五）。
- **展示口径**：商品评价列表只出"审核通过"的评价（既有契约注释"审核后展示"）；待审/驳回不出现在对外列表。
- **V1 审核口径（用户裁定 B，2026-09-22）**：新评价自动通过（`audit_status=1`），使评价功能即刻可用。
  **合规债务**：UGC 未经审核即公开，公开上线前必须补后台审核面（含审核列表/通过/驳回/商家回复）并切回"先审后发"——已记 PROGRESS §五。
- **后台审核面不在本批**：`IReviewLogic.Reply/Audit/PendingAudit` 三方法无 API 端点（死契约），本批只透出已存在的回复内容，不提供回复写入。
- **追评时效**：90 天以主评价的创建时间起算（既有契约注释）。
- **商家回复**：回复写入能力不在本批（无端点），但已存在的回复内容必须在列表/我的评价中透出。
- **评价与订单的关系**：仅"已完成"订单的订单项可评；不支持未收货评价、不支持删除/修改主评价（既有契约未提供）。
- **响应格式**：评价图片以 JSON 数组存空数组而非 NULL；评价人是会员（无多商户概念）。

## Dependencies

- 批次 06 已交付的订单/订单项快照（评价快照与"已完成"判定均依赖它）。
- 表 `product_review` 已存在（迁移 000012/000022），本批**预期零迁移**；若发现列缺失再按协议记账后补。
