## User Scenarios & Testing *(mandatory)*

> **本批性质（勘察结论）**：user 域的 `IProfileLogic/IAddressLogic/IFavoriteLogic/IFootprintLogic/
> INotifyLogic/IPointLogic` 等**均为接口、无实现**（与批次 04 的"连线收口"相反）——本批是**从零实现**。
> 接口方法注释已把行为钉死（脱敏/复活语义/跳过语义/欠款语义），规格据此验收。
> 全部行为基于既有表：user（含昵称/头像/性别 + V11/V19/V27/V28 扩展列）、user_address、user_favorite、

> invite_record。**唯一表结构缺口**：通知偏好无存储位置（无表无列）→ 本批新增迁移（见假设与 FR-015）。

### User Story 1 - 会员资料与登录记录（Priority: P1）🎯 MVP

会员查看个人资料（手机号**脱敏**、昵称、头像、性别、等级名称、成长值）、修改昵称/头像/性别、查看近 30 天登录记录（分页）。

**Why this priority**: 会员中心入口；成长值/等级是其身份与后续权益的基础。

**Independent Test**: 造会员（含等级规则）→ 查资料（手机号脱敏、等级名与成长值正确）→ 改昵称 → 再查已变更 → 登录记录含最近一条。

**Acceptance Scenarios**:

1. **Given** 会员手机号 138****1111，**When** 查资料，**Then** 返回脱敏手机号（中间四位掩码）、昵称、头像、性别、等级名称、成长值。
2. **Given** 会员，**When** 修改昵称/头像/性别，**Then** 再查资料反映新值；未传字段保持不变。
3. **Given** 会员有过登录，**When** 查登录记录（分页），**Then** 返回近 30 天记录、按时间倒序、总数正确。

### User Story 2 - 收货地址（Priority: P1）

会员维护收货地址：列表、新增、修改、删除、设为默认；默认地址唯一（设置时同事务清除其他默认标记）。

**Why this priority**: 下单必需（试算运费依赖地址区划码）；地址簿是会员高频操作。

**Independent Test**: 建两条地址 → 设其一为默认 → 另一条默认标记被清除 → 修改/删除生效 → 列表正确。

**Acceptance Scenarios**:

1. **Given** 会员无地址，**When** 新增地址（收件人/电话/省市区/详址），**Then** 成功返回 ID；首条自动为默认（或按既有规则）。
2. **Given** 两条地址（A 默认），**When** 设 B 为默认，**Then** B 默认且 A 的默认标记被清除（同事务，不留双默认）。
3. **Given** 地址 A，**When** 修改其详址，**Then** 仅该地址变更，默认标记不受影响。
4. **Given** 地址 A，**When** 删除，**Then** 列表不再含 A。
5. **Given** 他人的地址 ID，**When** 以当前会员操作（改/删/设默认），**Then** 拒绝（归属校验——越权防护）。

### User Story 3 - 收藏与足迹（Priority: P1）

会员收藏商品（列表含实时价态、加入、取消——软删后可重新加入=复活）与浏览足迹（列表、清空）。

**Why this priority**: 会员复访与转化的抓手；实时价态是收藏列表的价值所在（价格变化可见）。

**Independent Test**: 收藏两件商品 → 列表含实时价格与可售态 → 取消其一 → 再收藏（复活）→ 列表恢复 → 清空足迹后列表为空。

**Acceptance Scenarios**:

1. **Given** 上架商品，**When** 会员收藏，**Then** 收藏列表含该商品且带**实时价态**（价格/可售）。
2. **Given** 已收藏，**When** 取消收藏，**Then** 列表不再含（软删）；**再次收藏同一商品**，**Then** 复活（不产生重复行、不报唯一冲突）。
3. **Given** 商品已下架，**When** 查收藏列表，**Then** 该商品的可售态标记为不可售（仍可见，不静默消失）。
4. **Given** 会员有足迹，**When** 清空，**Then** 足迹列表为空；清空前列表按最近浏览倒序并含浏览次数。

### User Story 4 - 站内信与通知偏好（Priority: P2）

会员查看站内信（列表带**未读计数**）、标记单条已读、全部已读；查询与设置通知偏好（小程序订阅/短信两渠道的开关，站内信不在偏好内）。

**Why this priority**: 消息触达是交易闭环的用户侧出口；偏好决定渠道发送与否。

**Independent Test**: 造 3 条站内信（2 未读）→ 列表未读计数=2 → 标记一条已读 → 计数=1 → 全部已读 → 计数=0；设置短信关闭 → 查询反映关闭。

**Acceptance Scenarios**:

1. **Given** 会员有 3 条站内信（2 未读），**When** 查消息列表，**Then** 返回列表与**未读计数=2**；可按已读态筛选。
2. **Given** 未读消息，**When** 标记已读（单条/全部），**Then** 该消息已读 / 全部已读，未读计数相应减少。
3. **Given** 会员偏好（渠道：小程序/短信），**When** 设置某渠道为关闭，**Then** 再查偏好反映关闭；**站内信不出现于偏好列表**（其不受偏好控制）。
4. **Given** 未设置过偏好，**When** 查偏好，**Then** 返回默认全开（两渠道）。

### User Story 5 - 积分账户与流水（Priority: P2）

会员查看积分账户（余额/累计获得/累计消耗等）与积分流水（按业务类型筛选、分页）。

**Why this priority**: 积分是留客工具；账户与流水是会员对积分的可见性出口。

**Independent Test**: 造积分账户与流水 → 查账户 → 查流水（含类型筛选）→ 分页正确。

**Acceptance Scenarios**:

1. **Given** 会员积分账户，**When** 查账户，**Then** 返回余额与累计获得/消耗等字段。
2. **Given** 若干积分流水（不同业务类型），**When** 查流水（指定类型），**Then** 仅返回该类型且分页总数正确；不指定类型返回全部。

---

### User Story 6 - 邀请记录（Priority: P3）

会员查看自己的邀请记录（列表分页）。

**Why this priority**: 社交电商的裂变可见性；依赖既有 `invite_record`（V28 双时机）表。

**Independent Test**: 造邀请记录 → 会员查列表 → 仅见自己的记录且分页正确。

**Acceptance Scenarios**:

1. **Given** 会员有邀请记录，**When** 查询，**Then** 仅返回该会员发起的记录（越权防护），分页正确。

### Edge Cases

- 地址默认唯一性：并发设默认不应产生双默认（同事务清除 + 单条设置）。
- 收藏复活：软删行重新加入不得违反唯一约束（解除软删而非插入新行）。
- 足迹上报（内部方法 Record）非本批端点：重复浏览 UPSERT 更新计数与时间。
- 手机号脱敏在**服务层**完成（DO 出参不含明文；任何日志不得输出明文——延续 FR-007 类约束）。
- 偏好未设置时返回默认全开（不依赖预置行）。
- 积分余额可为负（欠款语义）：展示如实，不隐藏。
- invite_record 的路径在 `/distribution/` 下但归属本批（批次 06/11 的分销端点各自独立）。
- **本批新增 1 个迁移**（通知偏好表，spec 假设修订）；其余零表结构变更。

## Requirements *(mandatory)*

### Functional Requirements

**资料与登录记录**

- **FR-001**: 系统 MUST 提供会员资料查询：手机号**脱敏**、昵称、头像、性别、等级名称、成长值。
- **FR-002**: 系统 MUST 提供资料修改（昵称/头像/性别）；未传字段 MUST 保持不变。
- **FR-003**: 系统 MUST 提供近 30 天登录记录查询（分页、时间倒序）。

**收货地址**

- **FR-004**: 系统 MUST 提供地址列表、新增、修改、删除（归属校验：仅本人地址可操作）。
- **FR-005**: 系统 MUST 提供设默认地址：同事务清除该会员其他默认标记（默认唯一）。
- **FR-006**: 系统 MUST 在下单取址时校验地址归属并返回含区划码的地址（运费计算依据）——内部能力，本批不含端点。

**收藏与足迹**

- **FR-007**: 系统 MUST 提供收藏列表（含**实时价态**：价格与可售），取消收藏为软删，**再次收藏 MUST 复活**（不产生重复行）。
- **FR-008**: 系统 MUST 提供足迹列表（按最近浏览倒序、含浏览次数）与清空。

**站内信与通知偏好**

- **FR-009**: 系统 MUST 提供站内信列表（含**未读计数**、可按已读态筛选）、标记单条已读、全部已读。
- **FR-010**: 系统 MUST 提供通知偏好查询与设置（渠道：小程序订阅/短信）；**未设置时默认全开**；站内信不受偏好控制。
- **FR-011**: 通知偏好 MUST 持久化（本批新增存储）；设置 MUST 幂等（重复设置同值不产生重复行）。

**积分**

- **FR-012**: 系统 MUST 提供积分账户查询（余额与累计字段）与积分流水查询（按业务类型筛选 + 分页）。
- **FR-013**: 积分余额可为负（欠款语义）且 MUST 如实展示。

**邀请记录**

- **FR-014**: 系统 MUST 提供会员本人的邀请记录查询（分页、归属校验）。

**存储**

- **FR-015**: 系统 MUST 新增通知偏好存储（会员维度 + 渠道维度唯一），空库全量重放 MUST 零失败；回退脚本 MUST 可执行。

### Key Entities *(include if feature involves data)*

- **会员（user）**：昵称/头像/性别/手机号（密文+哈希索引）、成长值（V19/V27 扩展）、等级关联（user_level_rule）。
- **收货地址（user_address）**：收件人/电话/省市区划码/详址/默认标记。
- **收藏（user_favorite）**：会员×SPU，软删（复活语义）。
- **足迹（user_footprint）**：会员×SPU，最近浏览时间/浏览次数。
- **站内信（user_message）**：会员、标题/内容、已读态。
- **通知偏好（本批新增）**：会员×渠道（1小程序订阅 2短信）、开关。
- **积分（point_account/point_log）**：账户余额与累计；流水含业务类型/变动值/关联单号。
- **登录记录（user_login_log）**：时间、渠道、IP/UA 等。
- **等级规则（user_level_rule）**：等级门槛与名称。
- **邀请记录（invite_record）**：邀请人/被邀请人、时机标记（V28）。

## Assumptions

- **本批为从零实现**（user 域 8 个接口均无实现）；接口方法注释即行为契约。
- **新增 1 个迁移**（通知偏好表 `user_notify_preference`，会员×渠道唯一）——勘察确认无既有存储位置；原"零迁移"预期按此修订（记账）。
- 手机号脱敏在服务层完成（复用既有 `security.PhoneCipher` 与脱敏工具）。
- 会员等级名称由 `user_level_rule` 按成长值匹配（既有表）。
- `Record`（足迹上报）/`GetForOrder`（下单取址）/`Enqueue`（通知入队）/`Earn·Consume·Refund`（积分变动）等为内部方法，本批**实现但不暴露端点**（供交易链路与定时任务调用；交易链路已在 006 以自实现方式存在，本批不改其调用）。
- 收藏列表的"实时价态"取 SPU 的 price_min/price_max 与可售标记（与商品浏览同口径）。
- invite_record 虽在 `/distribution/` 路径下，归属本批（21 端点清单已定）。
- 批次 DoD：user 34→13；全量测试绿；本批文件 lint 零问题。
