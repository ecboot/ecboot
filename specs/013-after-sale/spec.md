## User Scenarios & Testing *(mandatory)*

### User Story 1 - 会员申请售后（Priority: P1）🎯 MVP

买家在"我的订单"里对某个订单项发起售后：选择"仅退款"（未收到货/不想要了）或"退货退款"（质量问题/发错货），填写数量、原因、可选凭证图片。系统必须能判断这笔申请是否成立：订单项属于本人、数量不超过该行购买数量、且该行累计已申请的售后数量不能超过购买数量（防重复/超额退）。

**Why this priority**: 售后入口是整条售后链路的第一环，也是资金外流的申请起点；校验不严会直接造成超额退款。它单独上线即可让买家"提得出申请"。

**Independent Test**: 造一个已完成订单 → 按其订单项申请售后 → 返回售后单号且状态为"待审核"；再对同一行申请超出剩余可退数量的售后 → 被拒绝（业务码），且售后单不落库。

**Acceptance Scenarios**:

1. **Given** 一笔本人已完成订单的订单项（数量 2，未申请过售后），**When** 申请"退货退款"数量 2，**Then** 创建售后单（状态 10 待审核），退款金额等于该行实付金额。
2. **Given** 该行已有一笔数量 2 的售后单，**When** 再次对该行申请数量 1，**Then** 拒绝并提示已达可退上限（累计口径），无新售后单。
3. **Given** 数量 2 的订单项，**When** 申请数量 3，**Then** 拒绝（数量超过购买数量）。
4. **Given** 他人订单的订单项，**When** 申请售后，**Then** 按"不存在"处理（不泄露他人资源）。
5. **Given** 仅退款的申请，**When** 数量 1，**Then** 退款金额按行实付的比例折算到分（部分退不退整行金额）。

### User Story 2 - 后台审核（Priority: P1）

客服/运营在后台看到售后申请列表与详情，做出"同意"或"拒绝"。同意时按类型分流：仅退款 → 直接进入"待退款"并**立即尝试发起渠道退款**；退货退款 → 进入"待买家寄回"。拒绝时必须填写原因，买家侧可见。

**Why this priority**: 审核是售后从"申请"走向"资金动作"的闸门；没有审核就没有后续流程。

**Independent Test**: 造待审核的仅退款单 → 后台同意 → 状态进入待退款并产生渠道退款请求；造待审核的退货退款单 → 后台拒绝并填原因 → 状态"已拒绝"，详情含拒绝原因。

**Acceptance Scenarios**:

1. **Given** 仅退款的待审核单，**When** 后台同意，**Then** 状态变为"退款中"（已发起渠道退款），买家详情可见退款时间；渠道失败时停留在"待退款"且可在后台重试。
2. **Given** 退货退款的待审核单，**When** 后台同意，**Then** 状态变为"待买家寄回"，不产生渠道退款。
3. **Given** 任意待审核单，**When** 后台拒绝并填写原因，**Then** 状态"已拒绝"且原因对买家可见。
4. **Given** 非"待审核"的单，**When** 再次同意或拒绝，**Then** 拒绝操作（状态不允许），状态不变。

---

### User Story 3 - 退货寄回与确认收货（Priority: P1）

退货退款的买家把货寄回后，在 C 端填写寄回物流单号；后台收到货后"确认收货"，售后单进入"待退款"，随后发起渠道退款。

**Why this priority**: 这是退货退款与仅退款的分叉点，缺它则退货退款的资金动作永远无法触发。

**Independent Test**: 待寄回的售后单 → 买家填寄回单号 → 后台确认收货 → 状态"待退款"→ 渠道退款请求已发出。

**Acceptance Scenarios**:

1. **Given** 状态"待买家寄回"的单，**When** 买家填写寄回单号，**Then** 详情可见该单号。
2. **Given** 未填写寄回单号的单，**When** 后台确认收货，**Then** 拒绝（缺寄回单号）。

---

### User Story 4 - 退款闭环与重试（Priority: P1）

渠道退款以"售后单号"作为对外的退款单号（幂等键）。退款结果回调到达时推进状态：退款中 → 已完成，不做二次退款。渠道明确失败时售后单停留在"待退款"，后台可"重试退款"再次发起。回调早到/重复到达/未匹配都必须被安全处理。

**Why this priority**: 这是本批唯一的"钱出去"的动作，幂等与重试语义是资金安全的核心。

**Independent Test**: 已发起退款的售后单 → 投递成功回调 → 状态"已完成"且退款时间落库；重复投递同一回调不改变状态；投递未匹配的回调被拒并留档。

**Acceptance Scenarios**:

1. **Given** 状态"退款中"的单，**When** 渠道退款成功回调到达，**Then** 状态"已完成"，退款时间落库。
2. **Given** 状态"已完成"的单，**When** 同一回调重复到达，**Then** 不重复推进（幂等），且失败通知不得被当作成功处理。
3. **Given** 状态"待退款"的单（渠道曾失败），**When** 后台重试退款，**Then** 重新发起渠道退款并回到"退款中"。

---

### User Story 5 - 会员查询与撤销售后（Priority: P2）

买家可以查看自己的售后列表（按状态筛选、分页）与详情（含进度与拒绝原因），并在申请尚未进入资金环节时撤销申请。撤销后该行的可退数量释放，可再次申请。

**Why this priority**: 提升体验与止损；不阻塞资金链路，故 P2。

**Independent Test**: 造两笔不同状态的售后单 → 列表按状态筛选命中 → 撤销未进入资金环节的单 → 状态"已撤销"且该行可退数量恢复。

**Acceptance Scenarios**:

1. **Given** 待审核的售后单，**When** 买家撤销，**Then** 状态"已撤销"，该订单项的可退数量恢复。
2. **Given** "待买家寄回"或"待退款"的售后单，**When** 买家撤销，**Then** 允许撤销（尚未进入资金环节）。
3. **Given** "退款中"（已发起渠道退款）的售后单，**When** 买家撤销，**Then** 拒绝（状态不允许）——在途资金不可中断。
4. **Given** 已完成的售后单，**When** 买家撤销，**Then** 拒绝（终态不可撤）。
5. **Given** 当前买家不是该售后单的申请人，**When** 查询详情/撤销，**Then** 按"不存在"处理。

---

### User Story 6 - 完成后的账实一致（Priority: P2）

售后单完成后，系统必须把账做实：回补库存（退货退款按退货数量；仅退款不回补）、更新订单的退款状态（无售后/部分退款/全额退款）、并对外发出"佣金冲销"事件（结算本身属分销批次）。

**Why this priority**: 数据一致性影响后续对账与分销结算；但可用增量补齐，故 P2。

**Independent Test**: 退货退款走完全流程 → 库存可售数量回补退货数量、订单退款状态变为"部分/全额退款"；仅退款走完 → 库存不变，订单退款状态仍被更新。

**Acceptance Scenarios**:

1. **Given** 退货退款完成，**When** 核对库存，**Then** 该 SKU 可售数量增加退货数量（锁定数量不变）。
2. **Given** 某订单的全部行都已售后退款完成，**When** 核对订单，**Then** 订单退款状态为"全额退款"；仅有部分行时為"部分退款"。
3. **Given** 售后完成，**When** 观察事件出口，**Then** 生成一条佣金冲销事件（结算动作不在本批）。

---

### Edge Cases

- 同订单项多笔售后并存：累计已退数量 + 本次申请数量 > 购买数量 → 拒绝（累计口径，非单笔口径）。
- 被拒绝的售后单占不占可退数量？（本规格：**不占**——拒绝即释放，买家可再申请，避免"驳回即锁死"。）
- 实付为 0 的订单项（全额优惠）：无资金可退 → 不发起渠道退款，直接以"已完成"收口（避免 0 元退款调用渠道）。
- 退款回调早于我方发起（回调先到）：必须不匹配、拒绝并留档，不得把未发起的单推成"已完成"。
- 撤销与在途退款并发：**已裁定（2026-09-22 用户选择 B）**——可撤状态限"待审核 / 待买家寄回 / 待退款"；已发起渠道退款的"退款中"及以上**不可撤**。理由：在途退款不可中断，若允许撤销将出现"钱已出、单已撤销"且回调因状态不符而不匹配的对账黑洞（与批次 06 的 C3a 静默资损面同型）。原接口注释"未终态→91撤销"据此收窄，已在 Assumptions 记明。
- 渠道退款失败：售后单停在"待退款"并留存失败原因，后台可重试。
- 同一售后单重复提交寄回单号：以最后一次为准（或拒绝），不得产生第二条售后单。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 会员必须能对**本人订单的某一个订单项**发起售后申请，类型限"仅退款"或"退货退款"。
- **FR-002**: 系统必须校验：订单项归属本人、申请数量 ≥1 且 ≤ 该行购买数量、该行**累计**已申请（未撤销/未拒绝）数量 + 本次 ≤ 购买数量；不满足时拒绝且不创建售后单。
- **FR-003**: 退款金额必须由系统计算（会员不可指定）：等于该行实付金额按数量比例折算到分；全额退时等于该行实付金额，且不得超过该行实付金额。
- **FR-004**: 售后单必须记录成因快照（订单号、订单项、用户、类型、数量、原因、描述、凭证图片、退款金额、币种）。
- **FR-005**: 会员必须能查询**自己的**售后列表（按状态筛选、分页）与详情；他人售后按"不存在"处理。
- **FR-006**: 后台必须能查询售后列表（按状态与类型筛选、分页）与详情（含买家信息与凭证）。
- **FR-007**: 后台必须能"同意"待审核的售后：仅退款 → 进入"待退款"并立即发起渠道退款；退货退款 → 进入"待买家寄回"。
- **FR-008**: 后台必须能"拒绝"待审核的售后，且**必须填写原因**，原因对买家可见；被拒绝的售后释放该行可退数量。
- **FR-009**: 退货退款的会员必须能填写寄回物流单号（仅"待买家寄回"状态可填）。
- **FR-010**: 后台必须能对已填寄回单号的退货退款单"确认收货"，使其进入"待退款"；缺少寄回单号时必须拒绝。
- **FR-011**: 渠道退款必须以**售后单号**作为对外退款单号（幂等键）；退款结果回调必须只推进"退款中 → 已完成"，失败通知不得被当作成功；未匹配/早到的回调必须被拒绝并留档。
- **FR-012**: 渠道退款失败时售后单必须停留在"待退款"并留存失败原因，后台必须能"重试退款"（不得重复推进已完成的单）。
- **FR-013**: 会员必须能撤销**尚未进入资金环节**的售后申请——可撤状态**仅限**"待审核 / 待买家寄回 / 待退款"；一旦已发起渠道退款（"退款中"）及任何终态（已完成/已拒绝/已撤销）一律不可撤（用户裁定 2026-09-22）。
- **FR-014**: 售后完成后必须回补库存：退货退款按退货数量回补可售数量；仅退款不回补。回补必须按数量而非整行。
- **FR-015**: 售后完成后必须更新订单的退款状态（无售后 / 部分退款 / 全额退款），口径按"该订单全部行的退款完成情况"。
- **FR-016**: 售后完成后必须对外发出"佣金冲销"事件（本批只留出口，结算与账务处理属分销/资金批次）——避免"退了款但佣金仍计提"。
- **FR-017**: 所有状态迁移必须是"条件更新"（并发下不重入）；重复请求不得产生重复资金动作。
- **FR-018**: 本批 11 个端点必须由 `CodeNotImplemented` 桩变为可用实现（SC-001 的数字化依据）。

### Key Entities *(include if feature involves data)*

- **售后单（after_sale_order）**：售后单号（对外兼退款幂等键）、所属订单与订单项、申请人、类型、状态（待审核/待寄回/待退款/退款中/已完成/已拒绝/已撤销）、币种、原因/描述/凭证、退款金额、寄回单号、渠道退款单号（回填）、拒绝原因、审核时间、退款完成时间。一单只对应一个订单项，可部分数量。
- **订单项（trade_order_item）**：提供行数量、行实付金额与行优惠分摊——退款金额与可退数量的计算依据。
- **订单（trade_order）**：持有退款状态（无售后/部分退款/全额退款），售后完成后被更新。
- **库存（inventory）**：退货退款完成后按数量回补可售数量（锁定数量不动）。
- **事件出口（佣金冲销）**：售后完成时投递的意图，供后续分销结算消费。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本批 11 个端点全部脱离"未实现"状态（桩数按渠道归零：shop 21→16、admin 64→58）。
- **SC-002**: 售后全链路可在一次演示中走通：申请 → 审核 → （退货：寄回 → 确认收货）→ 退款 → 完成，且每一跳状态可查。
- **SC-003**: 超额/重复申请 100% 被拒（累计口径），任意构造下都不会出现"同一订单项累计退款数量 > 购买数量"。
- **SC-004**: 重复退款回调 100% 幂等：同一售后单不会出现两次资金推进；已完成记录不被改写。
- **SC-005**: 售后完成后账实一致：库存回补数量、订单退款状态、退款金额三者与售后单可对账（既有交易链路回归零退化）。

## Assumptions

- **售后期窗口**：本批不设"订单完成后 N 天内才可申请"的时效限制（表结构无此字段），时效规则随运营配置另立。
- **拒绝释放额度**：被拒绝的售后单**不占用**可退数量（买家可再申请）；被撤销同理。
- **退款金额口径**：按**行实付**（已含行优惠分摊）比例折算；不单独处理运费（V1 包邮）。
- **渠道**：本批沿用 mock 渠道（真实微信/支付宝渠道另立特性）；退款应答语义与批次 06 的回调一致（失败必重试、成功幂等）。
- **分销/资金**：佣金冲销与余额退回的**结算**属分销与资金批次；本批只投递事件，不落账。
- **库存回补口径**：只回补可售数量，不触碰锁定数量（支付时已核销锁定）。
- **无多商户概念**：纯 B2C，售后不涉及商家/门店责任划分（门店自提的售后口径沿用订单渠道，不另立）。
- **依赖**：批次 06 已交付的订单/支付/退款回调（含幂等四层防线）为本批基础。**迁移**：实现期新增唯一迁移 **000038**（`after_sale_order` 补 `operator_id`/`fail_reason`）——原"无新表/零迁移"假设被实证推翻（D3 记录在案）。
- **口径修正（记录在案）**：`IAfterSaleLogic` 原注释写"未终态→91撤销"，本批按用户裁定收窄为"待审核/待寄回/待退款 可撤"（排除"退款中"）。实现时须同步该注释，避免下轮照旧注释写回。
- **被拒绝的售后单留痕**：拒绝原因必填且对买家可见；拒绝记录本身保留（审计），仅"可退数量"被释放。
