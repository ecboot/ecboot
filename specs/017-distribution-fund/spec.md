# Feature Specification: 分销与资金（批次11）

**Feature Branch**: `017-distribution-fund`

**Created**: 2026-09-22

**Status**: Draft

**Input**: 批次 11：分销与资金。**23 端点**（user 11 + admin 12，全为桩；`IDistributionLogic` user 侧 13 方法接口已有、admin 侧方法全缺）：**关系与资质**（申请/状态/邀请关系/审核/冻结）、**佣金计提与结算**（归因→规则命中→待结算→保护期满入账→退款冲销）、**账户与提现**（可负余额账户/流水/提现申请/审核/打款登记）、**邀请激励与推广码**。**宪法红线 #1：分销层级 ≤2 级**——`user_relation` 结构上仅存直接上级（无祖父列），应用层任何路径不得越级解析。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关系链与推广员资质（Priority: P1）🎯 MVP

用户申请成为推广员（后台审核通过后生效）；绑定直接上级（注册/首次归因时，一人一链、保护期外锁定）；查看我的上级与我邀请的下级（昵称脱敏）。后台可按状态筛选推广员、审核通过/拒绝、冻结/解冻（冻结不产生新佣金、存量可提现）。

**Why this priority**: 关系链是分销全部语义的根；**两级红线是宪法 #1（刑事级）**——绑定与解析路径的每一行都在红线之下。

**Independent Test**: A 邀请 B 注册（B 绑 A 为直接上级）→ B 申请推广员 → 后台通过 → B 状态=通过 → B 的关系页显示上级 A → A 的关系页显示下级 B → 冻结 B → B 状态=冻结。

**Acceptance Scenarios**:

1. **Given** 未申请用户，**When** 申请，**Then** 状态=1 待审核；重复申请 → 60001。
2. **Given** 待审推广员，**When** 后台审核通过，**Then** 状态=2 通过、audit_time 落库；审核动作对已终态记录重放 → 拒绝。
3. **Given** 通过的推广员，**When** 冻结，**Then** 状态=3；**When** 解冻，**Then** 回到 2；冻结期间不产生新佣金。
4. **Given** 用户 B 已绑上级 A，**When** B 再次绑定他人，**Then** 拒绝（一人一链，`uk_user` 结构强制）；**Given** B 绑定自己或自己的下级（互环），**Then** 应用层拒绝。
5. **Given** 关系页查询，**Then** 上级（若有）+ 下级分页列表，昵称全部脱敏。
6. **Given** 无关用户 C（未在任何链上），**When** 解析 C 的两级链，**Then** 只存在直接上级一级，无"祖父"概念可查。

### User Story 2 - 佣金计提、结算与冲销（Priority: P1）

订单**确认收货**时按订单项计提佣金：归因判定（分享窗口内归因人 > 关系链两级 > 自然流量不计佣）→ 按"商品覆盖 > 分类默认"命中规则 → 生成**待结算**记录（基数=订单项实付，不含运费/积分抵扣）。保护期（配置天数）满由结算任务批量**入账**（账户余额+、流水+、记录置已结算）。售后退款完成时**冲销**：未结算记录置失效；已结算记录生成**负额冲销记录**并从余额扣回（可负余额）。

**Why this priority**: 佣金是分销的资金核心；计提/结算/冲销三段的账实一致是资金域红线。

**Independent Test**: A 邀请 B，B 下单并确认收货（命中规则 L1=10%）→ 生成待结算记录（基数=行实付）→ 保护期满结算 → A 余额增加、流水可查 → 该项售后退款完成 → 负额冲销记录生成、A 余额扣回。

**Acceptance Scenarios**:

1. **Given** 规则（商品 S 覆盖 L1=10%/L2=5%，分类默认 L1=5%），**When** B 购买 S 确认收货（行实付 100.00），**Then** A（B 的直接上级）待结算记录 amount=10.00、A 的上级（二级）amount=5.00（若 A 有上级且二级比例>0）。
2. **Given** B 购买未命中任何规则的商品，**When** 确认收货，**Then** 不生成佣金记录（未命中不计佣）。
3. **Given** 分享窗口内 C 经 A 的分享链接购买（C 不在 A 的关系链上），**When** 确认收货，**Then** 归因 A 计佣（窗口外或无分享 → 关系链两级 → 均无则不计佣）。
4. **Given** 待结算记录与保护期配置 N 天，**When** 结算任务运行且期满，**Then** 记录置已结算、账户余额+、流水 biz_type=1；**When** 未期满，**Then** 不入账。
5. **Given** 已计提订单项发生售后退款完成，**When** 冲销执行，**Then** 未结算记录置 3 已失效；已结算记录生成负额冲销记录（reversal_of_id 回指）并余额扣回（可至负值）、流水 biz_type=5。
6. **Given** 冻结中的推广员名下订单确认收货，**Then** 不产生新佣金。
7. **Given** 同一订单项重复计提触发（事件重放），**Then** 只生成一次（订单项粒度幂等）。

### User Story 3 - 佣金账户与提现状态机（Priority: P1）

推广员查看佣金账户（可用余额可负/冻结金额）与**只追加**流水（余额/冻结双快照）。申请提现：余额校验 → 冻结（余额转冻结）→ 生成提现单（10 待审核）。后台审核：通过 → 20；拒绝 → 50 并**回退冻结到余额**。打款登记：成功 → 40（渠道单号回填，`uk_channel_order` 幂等防重复打款）；失败 → 60 并回退。

**Why this priority**: 提现是资金出账的唯一出口，状态机不可逆 + 双快照流水是资金安全的最后防线。

**Independent Test**: A 余额 100 → 申请提现 60 → 余额 40/冻结 60、单据 10 → 后台通过 → 20 → 打款成功（渠道单号 X）→ 40、冻结清零 → 同渠道单号再次登记 → 拒绝（幂等）。

**Acceptance Scenarios**:

1. **Given** 余额 100.00，**When** 申请提现 60.00，**Then** 提现单 10、余额 40.00、冻结 60.00、流水 biz_type=2；**When** 申请提现 200.00，**Then** 拒绝（余额不足）；金额 ≤0 或 >2 位小数 → 拒绝。
2. **Given** 提现单 10，**When** 审核拒绝（带原因），**Then** 状态 50、冻结回退余额、流水 biz_type=4。
3. **Given** 提现单 20，**When** 打款成功登记（渠道单号 X），**Then** 状态 40、冻结清零、流水 biz_type=3；**When** 相同渠道单号再次登记（任何单据），**Then** 拒绝（`uk_channel_order` 幂等）。
4. **Given** 提现单 20，**When** 打款失败登记（带原因），**Then** 状态 60、冻结回退、流水 biz_type=4。
5. **Given** 状态 10 的单据直接打款登记 / 状态 40 的单据再次审核，**Then** 全部拒绝（状态机不可逆，条件更新判行数）。
6. **Given** 可负余额（此前冲销扣为负），**When** 申请提现，**Then** 拒绝（余额不足，负余额不可提）。

### User Story 4 - 邀请激励、推广码与查询面（Priority: P2）

我的推广码（share_code + 分享链接）；邀请激励记录（新用户注册/首单双时机，一人一次）；C 端佣金比例查询（按商品：商品覆盖>分类默认）；C 端佣金记录/账户/流水/提现列表分页；admin 佣金记录（按状态/订单号筛选）与邀请激励记录列表。

**Why this priority**: 查询与激励面，无资金变更；依赖 US1-3 的数据落点。

**Independent Test**: 查推广码 → 返回码与链接 → 新用户经码注册 → 邀请激励记录（注册时机）生成一次 → 按商品查佣金比例 → 返回命中规则描述。

**Acceptance Scenarios**:

1. **Given** 用户，**When** 查推广码，**Then** 返回稳定 share_code 与分享链接（多次查询一致）。
2. **Given** 新用户经邀请注册，**When** 触发注册激励，**Then** invite_record 生成（trigger=1）；重复触发 → 不重复（一新用户仅一次）。
3. **Given** 商品命中商品级覆盖规则，**When** 查该商品比例，**Then** 返回覆盖值与作用域描述；未命中商品但命中分类 → 分类默认；均未命中 → 空列表。
4. **Given** 佣金记录/流水/提现列表查询，**Then** 分页正确、状态筛选正确、金额为两位小数字符串。

### Edge Cases

- **两级红线**：任何路径不得解析/存储第三级关系；`user_relation` 无祖父列，二级佣金解析=两次单列查询（上级的上级），到顶即止。
- **自邀/互环**：绑定上级=本人 → 拒绝；绑定形成环（A→B 且 B→A）→ 结构上不可能（一人一链），但应用层仍校验 inviter≠user。
- **并发提现**：同会员并发两笔提现申请，余额条件更新（`balance >= amount`）保证只有冻结得起的通过。
- **事件重放**：计提/冲销/结算任务重复触发，均以唯一业务键幂等（订单项+受益人+层级 不重复计提；结算任务只迁移待结算且期满的记录）。
- **冻结推广员**：不再计提新佣金，但既有余额可正常提现。
- **金额口径**：全程 `DECIMAL(10,2)` 元 / int64 分运算；比例 `DECIMAL(5,2)` %，佣金=基数×比例%（四舍五入到分，口径在实现期固化并注释）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1（资质）**: 申请（60001 防重）/状态/后台审核（条件更新状态机）/冻结解冻；推广员列表按状态与关键词筛选分页（昵称脱敏）。
- **FR-2（关系）**: 绑定直接上级（一人一链唯一键兜底+应用层自邀拒绝；保护期外锁定 V23 语义）；关系页上级+下级分页（脱敏）；两级解析到顶即止。
- **FR-3（计提）**: 确认收货事件 → 归因（分享窗口>关系链两级>不计）→ 规则命中（商品>分类，未命中不计）→ 待结算记录（订单项粒度幂等）；冻结推广员不计提。
- **FR-4（结算/冲销）**: 保护期满批量入账（余额+流水双快照+状态迁移，判行数）；退款冲销（未结算置失效/已结算负额冲销+扣回，可负余额）。
- **FR-5（提现）**: 申请（余额条件更新冻结+单据 10）/审核通过 20、拒绝 50 回退/打款成功 40（渠道单号唯一幂等）、失败 60 回退；状态机不可逆迁移全条件更新；流水 biz_type 1-5 全覆盖。
- **FR-6（激励/推广码）**: 邀请激励双时机（注册/首单）一人一次；推广码稳定返回。
- **FR-7（权限）**: 后台按路由注释挂权限点——distribution:audit（审核/冻结）、distribution:rule:read+manage（规则）、distribution:withdraw:read/audit/pay（提现）、distribution:read（记录/邀请记录列表）；7 权限点已全部在 000032 种子，**零权限迁移**。
- **FR-8（跨域钩子）**: 订单确认收货→计提、售后完成→冲销，经 shop 域 ports 投递（既有 ICommissionReverse 消费侧落地 + 新增正向投递端口），端口未装配降级告警（批次 07 同型）。

### Key Entities *(include if feature involves data)*

- `user_relation`（一人一链，uk_user；inviter_id 仅一级）、`distribution_user`（资质状态机）、`commission_rule`（uk_scope；比例两位百分数）
- `commission_record`（订单项粒度；status 1-4；冲销双列关联）、`user_account`（可负余额+frozen，uk_user）、`account_log`（只追加，双快照）
- `withdraw_order`（状态机 10/20/30/40/50/60；uk_withdraw_no、uk_channel_order）
- `invite_record`（双时机一人一次）、`share_record`（归因窗口源数据）、`user.share_code`

## Assumptions

- 提现打款 V1 为**后台人工登记**（`/admin/withdraws/{no}/pay`），真实渠道商家转账对接属后续批次；打款幂等由 `uk_channel_order` 承载。
- 结算保护期定时任务 V1 以**手动/测试触发**的 `ConfirmSettle` 服务方法交付（批量入账语义完整），cron 调度属部署面（`main.go` 定时器或外部触发，契约阶段裁定，不入端点）。
- 推广员等级（`distribution_user` 无 level 列，api 有 Level 字段）——V1 恒回 0/1 占位并记账（等级体系无表结构支撑）。
- 邀请激励的"奖励"内容以 invite_record.reward_desc 记录（批次 01 已有注册激励先例则复用其落点，勘察实现期确认）。
- 分享归因窗口的"窗口内归因人 > 关系链"优先级与窗口时长按 000028 配置化设计实现。
