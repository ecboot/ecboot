# Feature Specification: 全角色 API 接口面设计（依据业务数据表）

**Feature Branch**: `（未创建）`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "根据 apps/server/migrations 的业务数据表，设计出各个用例角色的 api 接口到 apps/server/api 目录中"

## User Scenarios & Testing *(mandatory)*

> 本特性是 **API 契约设计**：以既有 68 张业务表为事实依据，为三类用例角色（游客 / 会员 / 管理员）设计四渠道的完整接口面（路径、方法、入出参语义、权限、错误码），落入 api 目录的接口定义。**只交付接口契约层**（请求/响应结构与路由语义），不含业务实现（service/controller 的逻辑实现属后续实现特性）。
> 特性 003 已设计的登录链路 8 端点（验证码 3 + 登录 2 + 会话 3）**不在本特性重复设计**，本特性仅在其基础上扩展；两端点集合并构成本项目完整 API 面。

### User Story 1 - 游客浏览接口（Priority: P1）

未登录访客可以浏览商品分类/品牌/商品列表与详情（含规格与评价汇总）、搜索商品、查看营销活动（拼团/秒杀/砍价/助力/满减）、查看门店列表与详情（按区县/附近检索）、查看店铺运营位（轮播/楼层）内容。

**Why this priority**: 转化漏斗入口——游客能浏览是一切交易的前提；接口面最小闭环。

**Independent Test**: 仅携带公开端点清单即可 mock 出完整的"逛"体验（首页→分类→搜索→详情→活动页→门店页），全程无鉴权。

**Acceptance Scenarios**:

1. **Given** 游客打开首页，**When** 请求运营位与推荐商品，**Then** 返回轮播、楼层内容与在售商品列表，响应不含任何需登录字段。
2. **Given** 游客查看某商品详情，**When** 请求，**Then** 返回 SPU 信息、SKU 列表（含规格/价格/可售状态）、评价汇总（均值与分布），不暴露成本价等内部字段。
3. **Given** 游客请求按区县筛选营业门店，**When** 请求，**Then** 仅返回营业状态门店及其自提能力。

---

### User Story 2 - 会员交易接口（Priority: P1）🎯 MVP

登录会员可以：管理收货地址；操作购物车；创建订单（普通/拼团/秒杀/砍价成交单）、查询订单、取消订单、确认收货；发起支付与查询支付状态；申请售后（仅退款/退货退款）与撤销、填写寄回单号；提交评价与追评。

**Why this priority**: 交易闭环是平台的核心价值；本故事完成后"能买能退"。

**Independent Test**: 以会员凭证串起"加购→下单→支付状态→确认收货→评价→售后申请"全链接口调用，每步响应契约完整。

**Acceptance Scenarios**:

1. **Given** 会员已登录且购物车有商品，**When** 提交下单（含地址、优惠选择、幂等凭证），**Then** 返回订单号与应付金额；重复提交同凭证返回原订单（幂等）。
2. **Given** 订单待付款，**When** 会员取消，**Then** 订单进入已取消状态，接口返回成功；对已完成订单取消则被拒绝并返回明确错误码。
3. **Given** 已完成订单的某订单项，**When** 提交评价（评分/图文/匿名），**Then** 成功；重复提交同订单项返回"已评价"错误。

---

### User Story 3 - 会员资产与社交接口（Priority: P2）

登录会员可以：管理个人资料与查看等级成长值；管理积分（账户/流水）；管理优惠券（可领/可用/已用）与领券；管理收藏与足迹；使用消息中心（站内信列表/已读、订阅偏好）；使用分销中心（申请推广员、关系链、佣金记录与账户、提现申请、邀请记录、个人推广码）；查看登录记录；分享行为上报。

**Why this priority**: 社交电商的差异化能力；依赖交易接口提供的订单上下文（佣金/评价/积分消耗）。

**Independent Test**: 会员完成领券、积分查询、申请推广员、发起提现的接口调用序列，各响应契约完整且资金类接口带幂等语义。

**Acceptance Scenarios**:

1. **Given** 会员请求领取某优惠券，**When** 提交，**Then** 领券成功或返回"已领完/超限"明确错误码；重复请求不产生重复持有。
2. **Given** 推广员发起提现，**When** 提交金额超余额，**Then** 拒绝并返回余额不足错误码；合法金额则创建提现单返回单号。

---

### User Story 4 - 后台运营管理接口（Priority: P2）

管理员可以：管理商品（分类/品牌/SPU/SKU/两级上下架/限售区域）、库存（查询/调整）、订单（查询/详情/发货/取消）、售后（审核/确认收货退款）、促销（优惠券模板与发放、满减活动、拼团/秒杀/砍价/助力活动配置）、运营位（轮播/楼层）、门店管理、物流公司字典、分销管理（推广员审核/冻结、佣金规则、提现审核与打款）、会员管理（查询/禁用/改绑）。

**Why this priority**: 平台可运营的前提；与会员侧接口共享同一批业务表，契约需与 C 端语义一致（状态机约束相同）。

**Independent Test**: 以管理员凭证完成"创建 SPU+SKU→上架→库存调整→订单发货→售后审核"接口序列，各响应契约完整。

**Acceptance Scenarios**:

1. **Given** 管理员创建 SPU 与 SKU，**When** 提交，**Then** 返回编码；同一 SPU 下重复规格组合被唯一约束拒绝并返回明确错误码。
2. **Given** 待发货订单，**When** 管理员提交发货（物流公司+单号），**Then** 成功；对已发货订单重复发货被拒绝。

---

### User Story 5 - 后台治理接口（Priority: P3）

管理员可以：RBAC 管理（角色/权限树/账号-角色分配）、后台账号管理、审计查询（操作日志/登录日志）、风控管理（规则/事件/申诉）、系统配置查看与调整、运营看板（交易/会员/商品统计）。

**Why this priority**: 治理与合规的收口；依赖前两个后台故事的数据产生。

**Independent Test**: 管理员完成"建角色→配权限→建账号→查审计"接口序列；系统配置修改后读取返回新值。

**Acceptance Scenarios**:

1. **Given** 管理员为角色分配权限集合，**When** 提交，**Then** 全量替换成功并可回查。
2. **Given** 管理员修改系统配置项，**When** 再读取，**Then** 返回新值（生效机制属实现层）。

---

### Edge Cases

- 全部接口遵循统一响应契约（三段式）与既有错误码分段（1xxxx 通用 / 2xxxx 用户域，新增域按段位扩展）；参数校验失败标明字段。
- 分页接口统一分页参数与响应结构；列表接口必有排序语义说明。
- 会员访问他人资源（他人订单/地址/提现单）一律按不存在处理（不泄露存在性）。
- 回调类端点（支付/退款）为开放路径但必须验证渠道签名（语义上属"系统角色"，路由归 shop 渠道）。
- 管理端导出/批量类操作接口需声明幂等与范围上限语义。
- 砍价/助力等裂变接口的帮砍/助力动作天然是风控挂载点，契约中标注风控检查位。
- 手机号等敏感字段在响应中脱敏；管理端检索仅支持完整手机号精确匹配。
- 门店经纬度检索需声明距离排序语义；未配置经纬度的门店不参与附近检索。

## Requirements *(mandatory)*

### Functional Requirements

**契约总则**

- **FR-001**: 全部接口 MUST 遵循统一响应结构（状态码/消息/数据）与既有错误码分段；新增业务域错误码按段位追加并在契约中登记。
- **FR-002**: 接口 MUST 按角色标注鉴权级别：公开（游客）/ 会员（Bearer 凭证）/ 管理员（后台凭证+权限点）；权限点编码沿用既有 RBAC 命名规则（模块:资源:动作）。
- **FR-003**: 列表类接口 MUST 定义分页与排序语义；金额字段 MUST 声明单位（元，两位小数）。
- **FR-004**: 每个接口 MUST 定义：路径、方法、鉴权级别、入参（含必填与校验规则）、出参、可能的主要错误码。
- **FR-005**: 接口定义 MUST 按渠道目录归属（common/user/shop/admin），与既有目录结构一致；同一业务的 C 端与管理端接口语义（状态机约束）MUST 一致。

**游客（common + shop 渠道公开端点）**

- **FR-006**: MUST 提供商品分类树、品牌列表、商品列表（筛选/排序/分页）、商品详情（SKU/规格/评价汇总）公开接口。
- **FR-007**: MUST 提供关键词搜索接口（含筛选与排序参数）。
- **FR-008**: MUST 提供营销活动浏览接口：进行中的拼团/秒杀/砍价/助力活动列表与详情、活动商品与价格信息。
- **FR-009**: MUST 提供门店公开接口：门店列表（区县筛选/经纬度附近+距离排序）、门店详情。
- **FR-010**: MUST 提供运营位接口：轮播/弹窗（按位置与投放时段）、楼层内容。
- **FR-011**: MUST 提供满减活动与优惠券模板的公开浏览接口（可领列表供登录后领取）。

**会员交易（user + shop 渠道会员端点）**

- **FR-012**: MUST 提供收货地址 CRUD 与默认地址切换接口；地址携带省市区区划码。
- **FR-013**: MUST 提供购物车接口：加购/改量/移除/勾选/结算页试算（商品价态+优惠试算+运费试算）。
- **FR-014**: MUST 提供订单接口：创建（普通/拼团参团/秒杀/砍价成交，含幂等凭证）、列表（按状态筛选）、详情、取消、确认收货；下单 MUST 支持余额抵扣开关语义。
- **FR-015**: MUST 提供支付接口：发起支付（返回渠道唤起参数）、支付状态查询；并提供支付/退款回调开放端点（签名验证语义）。
- **FR-016**: MUST 提供售后接口：按订单项申请（仅退款/退货退款，含数量与凭证图）、撤销、填写寄回单号、进度详情、列表。
- **FR-017**: MUST 提供评价接口：提交（一项一评）、追评（一次）、商品评价列表（公开）、可评价订单项列表。

**会员资产与社交（user 渠道会员端点）**

- **FR-018**: MUST 提供个人中心接口：资料查看与修改、等级与成长值、（改密/设密如支持）。
- **FR-019**: MUST 提供积分接口：账户余额、流水列表；优惠券接口：可领模板列表、领取、我的券（按状态）。
- **FR-020**: MUST 提供收藏（增删/列表/复活语义）与足迹（列表/清空）接口。
- **FR-021**: MUST 提供消息中心接口：站内信列表/详情/已读/全部已读、通知偏好查看与设置。
- **FR-022**: MUST 提供分销中心接口：推广员申请与状态、关系链查询、佣金规则查询（可见比例）、佣金记录列表、账户（余额/冻结）、账户流水、提现申请/列表/详情、邀请记录、我的推广码。
- **FR-023**: MUST 提供分享上报接口（分享触点记录，供归因）与登录记录查询接口（近 30 天）。

**后台运营（admin 渠道管理员端点）**

- **FR-024**: MUST 提供商品管理接口：分类 CRUD、品牌 CRUD、SPU CRUD 与上下架、SKU 管理与启停、限售区域设置。
- **FR-025**: MUST 提供库存接口：库存查询、库存调整（留痕语义）、预警查询。
- **FR-026**: MUST 提供订单管理接口：列表（多条件筛选）、详情、发货、取消（管理员取消）、卖家备注。
- **FR-027**: MUST 提供售后管理接口：待审列表、同意/拒绝、退货确认收货、退款重试。
- **FR-028**: MUST 提供促销管理接口：优惠券模板 CRUD 与发放记录、满减活动（含档位与范围）、拼团/秒杀/砍价/助力活动 CRUD 与状态管理。
- **FR-029**: MUST 提供运营位管理（轮播/楼层 CRUD 与启停）、门店管理 CRUD、物流公司字典管理接口。
- **FR-030**: MUST 提供分销管理接口：推广员审核与冻结、佣金规则配置（分类/商品两级作用域）、佣金记录查询、提现审核与打款/失败回退、邀请激励记录查询。
- **FR-031**: MUST 提供会员管理接口：会员列表与详情（手机号精确检索、脱敏展示）、禁用/启用、手机号改绑、注销协助处理。

**后台治理（admin 渠道管理员端点）**

- **FR-032**: MUST 提供 RBAC 接口：角色 CRUD、权限树查询、角色-权限分配（全量替换）、账号-角色分配。
- **FR-033**: MUST 提供后台账号 CRUD 与状态管理、个人信息与改密接口。
- **FR-034**: MUST 提供审计查询接口：操作日志（按人/模块/时间筛选）、登录日志。
- **FR-035**: MUST 提供风控接口：规则 CRUD、事件查询、申诉处理（通过/驳回）。
- **FR-036**: MUST 提供系统配置接口：配置列表、修改（含类型与说明展示）。
- **FR-037**: MUST 提供运营看板接口：交易概览（订单数/销售额/退款）、会员概览（新增/活跃）、商品概览（在售/低库存）。

### Key Entities *(include if feature involves data)*

- 本特性不新增业务实体——接口契约映射既有 68 张表；契约层核心概念：
- **接口契约（Endpoint Contract）**: 路径/方法/鉴权级别/入参/出参/错误码的完整定义，按渠道归属。
- **鉴权级别（Auth Level）**: 公开 / 会员 / 管理员（含权限点）三级。
- **权限点（Permission Code）**: 模块:资源:动作 编码，与管理端 RBAC 权限树一一对应。
- **错误码（Error Code）**: 既有分段体系的域内扩展。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 接口清单覆盖全部 68 张业务表的读写场景，每张表至少有一个消费它的接口（只读表如日志类为查询接口）——覆盖率 100%。
- **SC-002**: 每个接口的契约六要素（路径/方法/鉴权/入参/出参/错误码）完整无缺项。
- **SC-003**: 三角色试用走查：游客逛、会员买、管理员管三条旅程的全部接口调用序列无契约缺口（无"下一步无接口可调"）。
- **SC-004**: 同一业务状态在 C 端与管理端接口中的约束语义一致（如订单取消条件、售后状态迁移）。
- **SC-005**: 全部接口定义落入 api 目录且通过编译检查（结构定义零错误）。
- **SC-006**: 鉴权级别标注覆盖率 100%；管理端写操作接口全部携带权限点编码。

## Assumptions

- 接口风格遵循项目既有约定：RESTful 语义、统一三段式响应、既有错误码分段与追踪号机制；具体路径命名在契约细化为 `/{渠道前缀}/{资源}` 风格。
- 特性 003 的登录链路 8 端点视为已设计，本特性契约清单中引用不重述；其契约若有修订随 003 演进。
- 回调端点（支付/退款）归属 shop 渠道开放路径，签名验证为实现层职责，契约只声明"需验证"语义。
- 接口契约的落地形态为 api 目录的接口定义（请求/响应结构体与路由元信息）；控制器与业务实现不在本特性范围。
- 管理端导出（Excel 等）V1 不做，仅声明可扩展；看板为只读统计接口，口径随实现细化。
- 短信/微信等外部渠道依赖延续 003 的 mock 约定；本特性的接口不直接依赖外部渠道。
- 店铺（store）为平台自营门店，无商家归属语义；不设计任何商家端（B2B2C）接口——宪法红线。
