## User Scenarios & Testing *(mandatory)*

> 交易支撑与内容运营批次：物流公司是发货环节的字典来源（订单发货选择），
> 运营装修是首页内容的配置载体（金刚区/商品楼层/专题，改版不发版）。
> 全部行为基于既有契约：logistics_company（000015：code 唯一、停用保留）、
> operation_banner（000026：position 位置、投放时段可配）、operation_floor（floor_type 三型、config JSON）、
> 权限码 logistics:company:manage / operation:banner:manage / operation:floor:manage（000032 种子）。
> 规格只验收行为；订单发货的物流选择消费（admin 订单发货）归交易批次（012）。

### User Story 1 - 物流公司字典管理（Priority: P1）

授权运营维护物流公司（编码、名称、运单号校验规则、排序、启停），支持列表（状态筛选 + 分页）、详情、软删除。编码全局唯一且不可改；停用公司保留在字典中（历史订单发货信息仍需可读），仅不再供新发货选择。

**Why this priority**: 发货是交易闭环的必经环节；无字典则订单无法选择承运商（012 批次的前置依赖）。

**Independent Test**: 建公司（编码唯一）→ 列表/详情可见 → 编码重复拒绝 → 停用后仍在列表（status=0）→ 软删后不可见。

**Acceptance Scenarios**:

1. **Given** 授权运营，**When** 以未占用编码创建物流公司，**Then** 成功返回 ID；以同编码再建则拒绝（编码唯一）。
2. **Given** 启用中的公司，**When** 置为停用，**Then** 列表仍可检出（状态为停用），详情可见（停用=保留字典项, 不再供新发货选择）。
3. **Given** 已存在公司，**When** 修改名称/校验规则/排序/状态，**Then** 列表与详情反映新值。
4. **Given** 软删公司，**When** 列表与详情访问，**Then** 均不再出现（资源不存在）。
5. **Given** 列表请求（状态筛选或分页），**When** 查询，**Then** 仅返回匹配行且分页总数正确。

---

### User Story 2 - 运营装修配置管理（Priority: P1）

授权运营维护首页轮播/弹窗（位置、图片、跳转链接、排序、投放时段、启停）与首页楼层（类型：金刚区/商品楼层/专题、标题、配置 JSON、排序、启停），均支持列表、详情性字段返回、修改与软删除。

**Why this priority**: 首页内容运营是商城门面；内容配置与代码解耦（改版不发版）是本项目的既有设计取向（000026 表注释）。

**Independent Test**: 建轮播（位置=首页轮播）→ 列表按位置筛选可见 → 建楼层（type=金刚区，config 含入口数组）→ 列表可见 → 软删后不可见。

**Acceptance Scenarios**:

1. **Given** 授权运营，**When** 创建轮播（位置/图片必填），**Then** 成功；位置域外值拒绝（仅首页轮播/弹窗）。
2. **Given** 轮播列表请求带位置筛选，**When** 查询，**Then** 仅返回该位置的行且分页正确。
3. **Given** 创建楼层（类型为三型之一、config 为任意 JSON 对象），**When** 提交，**Then** 成功；类型域外值拒绝。
4. **Given** 已有轮播/楼层，**When** 修改（含投放时段、启停、config），**Then** 变更生效并在列表/详情可见。
5. **Given** 软删轮播或楼层，**When** 各管理端点与 C 端展示访问，**Then** 均不再出现。

---

### User Story 3 - C 端装修展示（Priority: P1）🎯 MVP

游客（无需登录）按位置获取当前**在投**的轮播/弹窗（启用且处于投放时段内，按排序），以及对首页楼层内容：启用楼层按排序返回，其中**商品楼层需装配商品摘要**（配置中的商品 ID 列表 → 商品名称/图片/价格），失效或下架商品被剔除而非报错。

**Why this priority**: 装修内容的最终消费方是 C 端首页；"在投"过滤与商品装配是这份数据的价值所在。

**Independent Test**: 造三条轮播（在投/未到时段/已过期）→ 游客仅见在投那条；造商品楼层（config 含 2 个有效 + 1 个失效商品）→ 返回 2 个商品摘要。

**Acceptance Scenarios**:

1. **Given** 位置=首页轮播的三条记录（一条无时段、一条未到开始时间、一条已过结束时间），**When** 游客按该位置请求，**Then** 仅返回无时段（长期）那条；未到时段与已过期被排除（投放语义）。
2. **Given** 停用的轮播，**When** 游客请求，**Then** 不出现。
3. **Given** 游客请求位置域外值，**When** 提交，**Then** 拒绝（位置仅两型）。
4. **Given** 启用楼层（金刚区 + 商品楼层 + 专题），**When** 游客请求楼层内容，**Then** 按排序返回全部启用楼层；金刚区/专题返回配置原样，商品楼层返回**商品摘要列表**。
5. **Given** 商品楼层配置含已下架/不存在的商品 ID，**When** 游客请求，**Then** 该商品被剔除（返回其余有效商品，不报错）。
6. **Given** 停用的楼层，**When** 游客请求，**Then** 不出现。

### User Story 4 - 权限挂接（Priority: P2）

三个写操作族按权限点校验：物流公司（`logistics:company:manage`）、轮播（`operation:banner:manage`）、楼层（`operation:floor:manage`），持权放行、无权拒绝、超管直通；查询类端点仅要求登录；C 端展示完全公开。

**Why this priority**: 延续批次 01/02 的 RBAC 机制；装修内容与发货字典可被任意登录管理员篡改是不可接受的。

**Independent Test**: 无权账号调三类写操作均被拒；超管放行；持 banner 权限但不持 floor 权限者建轮播成功、建楼层被拒。

**Acceptance Scenarios**:

1. **Given** 不持 `operation:banner:manage` 的账号与超管，**When** 各自调"新增轮播"，**Then** 无权限者被拒、超管成功。
2. **Given** 持 `logistics:company:manage` 但不持 `operation:floor:manage` 的账号，**When** 分别调"新增物流公司"与"新增楼层"，**Then** 前者成功、后者被拒（权限点各管一摊）。
3. **Given** 游客（未登录），**When** 调 C 端轮播/楼层端点，**Then** 正常返回（公开）。

### Edge Cases

- 轮播时段只配一端（仅开始 或 仅结束）：另一端视为长期有效（NULL 语义）。
- 轮播时段起止反置（开始晚于结束）：本批不校验（运营自行负责；如需校验属后续加固），C 端按区间判断自然不命中。
- 楼层 config 为空或非对象：金刚区/专题允许空配置（原样返回空）；商品楼层配置无商品 ID 列表时返回空商品摘要。
- 物流公司编码修改：不支持（编码是订单发货信息的存储值，改码会割裂历史）——修改仅及名称/规则/排序/状态。
- 楼层排序并列：按 id 兜底（稳定次序）。
- 本批不改任何表结构；零新迁移。

## Requirements *(mandatory)*

### Functional Requirements

**物流公司字典（admin）**

- **FR-001**: 系统 MUST 提供物流公司列表：状态筛选 + 分页（按表内 sort、id 稳定序；**契约未暴露 sort 字段**，运营不可配）。
- **FR-002**: 系统 MUST 提供物流公司创建：编码与名称必填，**编码全局唯一**（重复拒绝）；运单号校验规则可选；新建默认启用。
- **FR-003**: 系统 MUST 提供物流公司修改：名称/校验规则/状态（全量覆盖）；**编码不可修改**（订单发货存编码值，改码割裂历史；api 入参无该字段）。
- **FR-004**: 系统 MUST 提供物流公司软删除；删除后列表与详情均不可见。
- **FR-005**: 系统 MUST 提供物流公司详情；不存在返回资源不存在错误。
- **FR-006**: 停用的公司 MUST 保留在字典中（列表可见、详情可见），仅语义上不再供新发货选择。

**运营装修（admin）**

- **FR-007**: 系统 MUST 提供轮播列表（位置筛选 + 分页）与创建（位置/图片必填，位置仅两型）、修改（含投放时段与启停）、软删除。
- **FR-008**: 系统 MUST 提供楼层列表（分页）与创建（类型仅三型、标题、配置 JSON、排序）、修改、软删除。
- **FR-009**: 装修内容的软删除 MUST 同时从 C 端展示中移除。

**C 端展示（shop，公开）**

- **FR-010**: 系统 MUST 提供按位置的游客轮播列表：仅返回**启用且当前处于投放时段内**的记录，按排序、id 稳定序；时段为空的一端视为长期有效。
- **FR-011**: 系统 MUST 提供游客楼层列表：仅返回启用楼层，按排序、id 稳定序；返回类型、标题与配置。
- **FR-012**: 商品楼层（类型=商品楼层）MUST 装配商品摘要：按配置中的商品 ID 列表返回名称/图片/价格；**失效（下架/删除/不存在）商品 MUST 被剔除**而非报错。
- **FR-013**: 游客端点 MUST 无需登录可访问。

**权限**

- **FR-014**: 三类写操作 MUST 按权限点校验（`logistics:company:manage` / `operation:banner:manage` / `operation:floor:manage`）：持权放行、无权拒绝（权限不足错误码）、超管直通；查询仅要求登录。

### Key Entities *(include if feature involves data)*

- **物流公司（logistics_company）**：编码（全局唯一、不可改）、名称、运单号校验规则描述、排序、状态（1启用 0停用）、软删标记。
- **轮播（operation_banner）**：位置（1首页轮播 2首页弹窗）、图片、跳转链接、排序、投放起止（可空=立即/长期）、状态、软删标记。
- **楼层（operation_floor）**：类型（1金刚区 2商品楼层 3专题）、标题、配置（JSON 对象）、排序、状态、软删标记。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本批 15 个端点全部可调用，`make check-stub` 中 admin 渠道桩数由 104 降至 91（admin 13 端点）、common 渠道由 1 降至 1、shop 渠道由 42 降至 40（shop 2 端点）。

- **SC-003**: 商品装配可验证：配置含失效商品时返回其余有效商品摘要且不报错（行为级测试）。

- **SC-005**: `make test` 全绿（含既有回归），本批文件 lint 零问题。

## Assumptions

- 物流公司编码由运营指定（业务编码，非系统生成）——与门店编码（sonyflake 生成）不同：编码是订单发货信息的存储值，人工可读且稳定。
- 物流公司**无排序字段以外的运营态**；列表默认按 sort,id。
- 轮播时段语义：`start_time` 为 NULL 或 <= 当前 → 已开始；`end_time` 为 NULL 或 >= 当前 → 未结束；两者同时满足才在投。
- 楼层配置的商品 ID 列表：约定配置 JSON 中的商品 ID 字段名（实现期按既有前端约定确定并在契约注明）；本批不引入配置 schema 校验（config 为任意 JSON 对象）。
- 商品摘要装配在 shop 域内完成（同域直读商品表，不跨域事件）。
- `ILogisticsLogic` 缺 Detail 方法——按 D6 模式微扩（复用 LogisticsCompany 返回）。
- **装修域 service 接口与 DTO 不存在**——本批新建（属计划内新增，非微扩）：接口落 `service/shop`（装修是商城内容、物流是交易字典，同域），DTO 落 `model/dto_shop.go` 并带域前缀命名。
- 零表结构变更、零新迁移（三表齐备）。
- 批次 DoD：admin 104→91、shop 42→40（本批 15 端点清零）；全量测试绿；本批文件 lint 零问题。
