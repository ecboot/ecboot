- Q: 分销佣金比例的配置作用域？ → A: 分类默认+商品覆盖（作用域含分类/商品两级，命中优先级：商品 > 分类，未命中不计佣）

## User Scenarios & Testing *(mandatory)*

> **范围界定**：本特性交付的是 P0/P1/P2 各域的**数据模型**——表结构、约束、索引、迁移脚本与设计文档。
> 任何业务流程实现（服务代码、接口、前端、通知发送、任务调度、搜索引擎落地）均不在范围内。
> 以下用户故事均为"数据能力切片"：单独交付该域的 Schema 即构成可独立验证的增量。

### User Story 1 - 隐私与账号安全数据模型（Priority: P1）

用户手机号改为密文存储并以不可逆哈希列支撑登录检索与唯一性；新增用户登录日志表；定义注销匿名化的数据规则（哪些列被抹除/替换、唯一索引如何保持有效）。

**Why this priority**: 合规强制；且这是对既有 `user` 表的结构改造，必须在用户数据积累前完成，具有时序不可逆性。

**Independent Test**: 迁移脚本在既有库上执行成功后，`user` 表具备密文手机号列与哈希唯一索引，登录日志表可记录每次登录的结果与来源，注销匿名化规则在文档中可执行。

**Acceptance Scenarios**:

1. **Given** 既有 `user` 表含明文手机号与唯一索引，**When** 执行迁移，**Then** 表结构变为密文列+哈希唯一索引，且迁移脚本包含存量数据密文化的处理步骤。
2. **Given** 一个已注销（匿名化）的用户记录，**When** 用原手机号注册新账号，**Then** 不发生唯一索引冲突，新旧账号数据互不干扰。

---

### User Story 2 - 商品评价数据模型（Priority: P1）

评价表以订单项为粒度（一项一评），含评分、图文、匿名、审核状态、追评与商家回复；商品页汇总统计（均值、星级分布）可由该表推导。

**Why this priority**: 评价是电商闭环最后一块数据缺口；其结构必须锚定订单项快照，设计错了难以返工。

**Independent Test**: 评价表建好后，"同一订单项不可插入第二条主评价"由数据库唯一约束直接拒绝。

**Acceptance Scenarios**:

1. **Given** 某订单项已存在主评价，**When** 再插入一条同订单项主评价，**Then** 违反唯一约束被数据库拒绝。
2. **Given** 被评价商品已软删除，**When** 查询该评价，**Then** 评价行自洽（含商品快照信息或有效引用），无悬挂依赖。

---

### User Story 3 - 收藏与足迹数据模型（Priority: P2）

收藏表（用户×商品唯一）与足迹表（用户×商品唯一+最近浏览时间，有限保留期）。

**Why this priority**: C 端高频数据，结构简单但需在数据量增长前定去重与保留策略。

**Independent Test**: 同一用户对同一商品第二次收藏被唯一约束拒绝；足迹表按最近时间更新的写法在文档中有明确语句示例。

**Acceptance Scenarios**:

1. **Given** 用户已收藏商品 X，**When** 再次插入 (用户, X)，**Then** 唯一约束拒绝。
2. **Given** 足迹表按（用户, 商品）唯一，**When** 重复浏览，**Then** 设计文档定义的更新语义是更新最近浏览时间而非新增行。

---

### User Story 4 - 消息通知数据模型（Priority: P2）

异步通知任务表（渠道、模板、参数、状态机、重试计数、下次重试时间）与站内消息表（必达兜底）。

**Why this priority**: 通知发送是应用层的事，但任务队列的状态字段与重试语义必须先有承载结构。

**Independent Test**: 通知任务表的状态枚举覆盖 待发送/已发送/失败/已重试上限，重试计数与下次重试时间字段齐备。

**Acceptance Scenarios**:

1. **Given** 一条发送失败的通知任务，**When** 查看其数据，**Then** 重试计数已累加、下次重试时间已更新、终态有明确枚举值。
2. **Given** 用户关闭某渠道订阅，**When** 通知任务创建，**Then** 任务行可表达"渠道被跳过"的语义（状态或渠道字段）。

---

### User Story 5 - 物流公司字典（Priority: P2）

物流公司表：名称、编码、启用状态、单号校验规则描述。

**Why this priority**: 发货数据的最小前置；一单多包裹拆单表明确不在本期（演进预留）。

**Independent Test**: 字典表可维护≥1 条启用物流公司，`trade_order` 既有发货字段与其衔接方式在设计文档中明确。

**Acceptance Scenarios**:

1. **Given** 运营停用某物流公司，**When** 查看字典，**Then** 停用记录保留（软删/状态位），历史订单对该公司的引用不受影响。

---

### User Story 6 - 分销推广数据模型（Priority: P3）

两级封顶的邀请关系链表；推广员资质表；按商品配置的一二级佣金规则表；按订单项产生的佣金记录表（含冲销语义）；用户佣金账户（可用/冻结）与流水表；提现单状态机表；邀请注册激励记录表。

**Why this priority**: 社交电商的数据分水岭。关系链表的结构必须**从数据模型上无法表达第三层**（合规红线）；佣金与账户涉及资金，冲销与欠款语义必须落地到列与约束。

**Independent Test**: 关系链表仅有"上级"单列（无祖父列、无自引用多层路径），插入数据不可能构造三层佣金关系；佣金记录表的金额基数锚定订单项实付。

**Acceptance Scenarios**:

1. **Given** A←B←C 的两级关系链数据，**When** 尝试为 C 建立下级 D 并让 A 从 D 的订单获利，**Then** 表结构上不存在可承载该关系的列/路径。
2. **Given** 已结算佣金对应的订单项发生退款，**When** 写入冲销记录，**Then** 账户余额可为负（欠款）且流水完整可追溯（冲销记录关联原佣金记录）。
3. **Given** 提现单打款渠道可能重复回调，**When** 设计提现单状态字段，**Then** 存在幂等语义（条件更新可表达、状态枚举含打款中/成功/失败回退）。

---

### User Story 7 - 拼团数据模型（Priority: P3）

拼团活动表（成团人数、成团价、时限、限购）、团表（团长、状态、过期时间）、团员表（团×订单唯一绑定）；订单表增加团关联列。

**Why this priority**: 完全复用既有订单/库存模型，仅需增量表；超时解散退款的编排是应用层任务。

**Independent Test**: 同一用户在同一团只能有一条有效团员记录（唯一约束）；订单关联列可为空（普通订单不受影响）。

**Acceptance Scenarios**:

1. **Given** 用户已参团（存在团员记录），**When** 再次插入同团同用户的团员记录，**Then** 唯一约束拒绝。
2. **Given** 普通订单（非拼团），**When** 写入订单行，**Then** 团关联列为空不影响任何既有约束与索引。

---

### User Story 8 - 秒杀数据模型（Priority: P3）

秒杀活动表（时段、限购）与场次商品表（秒杀价、活动限量、已售——与普通库存分账）；订单项可记录秒杀价快照。

**Why this priority**: "不超卖"由既有库存条件更新模型在应用层保证，Schema 职责是活动库存与普通库存分账、取消回补的活动侧落点。

**Independent Test**: 场次商品表有独立的限量与已售列，与 `inventory` 表无耦合；订单项金额列可直接承载秒杀价。

**Acceptance Scenarios**:

1. **Given** 秒杀活动限量 100 件，**When** 查看场次商品行，**Then** 活动限量与已售独立于普通库存表达，扣减/回补语义在设计文档中有明确条件更新语句。
2. **Given** 秒杀订单项，**When** 查看订单项，**Then** 成交单价即秒杀价，金额类型与全库规范一致（DECIMAL(10,2)）。

---

### User Story 9 - 积分与会员等级数据模型（Priority: P4）

积分账户与流水表（获取/消耗/回退，可负余额语义）；会员等级规则表（成长值门槛、权益配置）；用户表等级扩展；订单层积分抵扣的分摊表达。

**Why this priority**: 积分抵扣会扩展订单优惠分摊语义，数据模型必须先定义"积分抵扣额"在订单/订单项上的落点。

**Independent Test**: 订单表的优惠构成可同时表达优惠券、积分、满减三部分且合计恒等约束在文档中给出校验语句。

**Acceptance Scenarios**:

1. **Given** 一笔使用积分+优惠券的订单，**When** 落库，**Then** 两类优惠在订单与订单项层均有独立列承载，分摊合计恒等关系可被校验 SQL 验证。
2. **Given** 用户积分全退（退款回退超过余额），**When** 写入回退流水，**Then** 账户余额为负不被约束拒绝（欠款语义由文档定义）。

---

### User Story 10 - 满减活动数据模型（Priority: P4）

满减活动表（时段、范围：全场/分类/商品）与档位表（满 X 减 Y 多档）；订单命中活动与档位的关联表达。

**Why this priority**: 与优惠券互补；范围限定（分类/商品集合）的数据表达是这个域唯一的结构难点。

**Independent Test**: 一个活动可挂多档位；范围限定可表达"全场"与"指定分类/商品"两种形态且查询高效。

**Acceptance Scenarios**:

1. **Given** 满减活动含 100-10 与 200-30 两档，**When** 查询该活动档位，**Then** 两档各行独立、档位门槛唯一。
2. **Given** 订单命中某活动某档，**When** 落库，**Then** 订单行可追溯命中的活动与档位（关联列）。

---

### User Story 11 - 风控数据模型（Priority: P4）

风控规则表与风控事件表（命中对象、规则、处置结果、申诉状态）。站内搜索**不建表**（商品既有结构已足够，搜索实现属技术层）。

**Why this priority**: 营销与分销玩法上线后资金面暴露，拦截记录必须可追溯；搜索从 Schema 视角零增量，显式声明以封边界。

**Independent Test**: 风控事件可关联用户/订单/优惠券等对象并记录处置与申诉流转。

**Acceptance Scenarios**:

1. **Given** 某账号被拦截一次领券，**When** 查看风控事件，**Then** 事件行含命中规则、对象类型与标识、处置结果、申诉状态。

### Edge Cases

- 存量明文手机号密文化：迁移脚本必须含数据迁移步骤，迁移期内新旧列并存策略与回滚方案。
- 注销匿名化 vs 唯一索引：手机号哈希列替换为墓碑值（如 `del_{id}_{hash前8位}`），保唯一且不可反推。
- 评价 vs 商品软删：评价保留展示（用户内容），以快照列或稳定引用承载商品标题。
- 佣金冲销欠款：账户余额允许负值，流水必须双向（原始/冲销关联）。
- 秒杀取消回补：回补落活动已售列（已售减），不落普通库存。
- 拼团参团未支付：团员记录与订单超时取消的联动语义（名额释放）在文档定义。
- 积分负余额：约束不用无符号列。
- 满减档位门槛唯一：同活动同门槛唯一约束。
- 提现打款重复回调：状态机条件更新幂等（同支付回调总则）。
- 通知任务重试上限后归档：终态枚举完备，不无限重试。

## Requirements *(mandatory)*

### Functional Requirements

**通用数据规范（沿既有决策）**

- **FR-001**: 所有新表 MUST 遵循既有全局约定：InnoDB、utf8mb4、`领域前缀_snake_case` 命名、`created_at`/`updated_at` 数据库维护、不建物理外键、关联列必建索引。
- **FR-002**: 所有金额列 MUST 为 `DECIMAL(10,2)`、币种语义沿用头表；所有枚举 MUST 为 TINYINT+注释穷举；主数据软删、交易单据与日志永不删除的边界 MUST 延续。
- **FR-003**: 全部交付 MUST 以增量迁移脚本（V11 起顺序编号）表达，在已应用 V1~V10 的库上可顺序执行成功，且不修改任何既有表数据的语义（新增列/表为主，既有列改造仅限 User Story 1 的手机号加密）。

**隐私与账号安全**

- **FR-004**: `user` 表 MUST 具备手机号密文列与不可逆哈希列，唯一索引 MUST 落在哈希列；迁移脚本 MUST 包含存量明文的密文化步骤；加密后检索能力 MUST 限定为完整手机号精确匹配（不提供模糊/尾号检索，不保留任何明文片段列）。
- **FR-005**: 系统 MUST 新增用户登录日志表（用户、结果、来源 IP、时间），只追加。

**评价**

- **FR-006**: 评价表 MUST 以订单项为粒度施加"一项一评"唯一约束，MUST 含评分（1-5）、内容、图片集、匿名、审核状态、追评（一次）、商家回复（一次）的承载列。

**收藏 / 足迹**

- **FR-007**: 收藏表 MUST 以（用户, 商品）唯一；足迹表 MUST 以（用户, 商品）唯一并携带最近浏览时间。

**通知**

- **FR-008**: 通知任务表 MUST 含渠道、模板标识、参数载体、状态机枚举（待发送/已发送/失败/达重试上限/跳过）、重试计数与下次重试时间；站内消息表 MUST 支持已读状态。

**物流**

- **FR-009**: 物流公司字典表 MUST 含名称、编码（唯一）、启用状态、单号校验规则描述，主数据软删。

**分销**

- **FR-010**: 关系链表 MUST 仅以"直接上级"单列表达层级，结构上 MUST NOT 存在可承载第三层及以上佣金关系的列或路径；同一用户 MUST 至多一条关系记录。
- **FR-011**: 佣金规则 MUST 支持分类级默认与商品级覆盖两种作用域，命中优先级为 商品 > 分类，均未命中不计佣；佣金记录 MUST 关联订单项与受益人、含状态枚举（待结算/已结算/已失效/欠款冲销中）并可关联其冲销记录。
- **FR-012**: 用户佣金账户 MUST 区分可用/冻结余额，余额 MUST 允许负值；全部变动 MUST 有流水，流水 MUST 可关联原始记录（冲销场景）。
- **FR-013**: 提现单 MUST 具备 申请→审核→打款中→成功/失败回退 的状态枚举与幂等语义承载（渠道单号唯一）。
- **FR-014**: 邀请激励记录 MUST 以新用户唯一，发放语义幂等。

**拼团**

- **FR-015**: 团员表 MUST 以（团, 用户）唯一并与订单号唯一关联；团表 MUST 含状态（拼团中/已成团/已解散/超时）与过期时间；订单表 MUST 增加可空团关联列。

**秒杀**

- **FR-016**: 场次商品表 MUST 独立表达活动限量与已售（与普通库存分账），MUST 含秒杀价与限购数；活动表 MUST 含起止时间。

**积分 / 等级**

- **FR-017**: 积分账户与流水 MUST 分表，流水含来源/用途枚举；账户余额 MUST 允许负值。
- **FR-018**: 订单/订单项的优惠构成 MUST 可分别表达优惠券、积分、满减三项，且"订单优惠总额=订单项分摊合计"恒等，校验语句 MUST 在设计文档给出。
- **FR-019**: 会员等级规则表 MUST 含成长值门槛（唯一递增）与权益配置载体；成长值 MUST 与积分双账本分离、独立承载且只增不减；用户等级列 MUST 可空（未启等级体系时零影响）。

**满减**

- **FR-020**: 满减活动 MUST 支持多档位子表（同活动同门槛唯一）与范围表达（全场/分类集合/商品集合），范围数据 MUST 支持高效命中查询。

**风控**

- **FR-021**: 风控规则与事件表 MUST 分离；事件 MUST 可关联多种业务对象（用户/订单/券等）并记录处置结果与申诉状态。

### Key Entities *(include if feature involves data)*

- **评价（Review）**: 订单项粒度，一项一评，含追评/回复/审核/匿名。
- **收藏 / 足迹（Favorite / Footprint）**: 用户×商品唯一关系，足迹含最近浏览时间。
- **通知任务 / 站内消息（NotifyTask / UserMessage）**: 渠道化异步队列与兜底消息。
- **物流公司（LogisticsCompany）**: 承运方字典。
- **用户关系（UserRelation）**: 两级封顶邀请关系链（直接上级单列）。
- **推广员（DistributionUser）**: 推广资质与状态。
- **佣金规则 / 佣金记录（CommissionRule / CommissionRecord）**: 分类默认+商品覆盖的作用域化比例配置（商品>分类）；订单项佣金流水与冲销。
- **用户账户 / 流水 / 提现单（UserAccount / AccountLog / WithdrawOrder）**: 佣金资金载体（可负余额、幂等打款）。
- **邀请激励记录（InviteRecord）**: 新用户唯一的拉新激励凭证。
- **拼团活动 / 团 / 团员（GroupBuyActivity / Team / TeamMember）**: 成团规则与成员订单绑定。
- **秒杀活动 / 场次商品（FlashSaleActivity / FlashSaleItem）**: 时段限购与活动分账库存。
- **积分账户 / 流水（PointAccount / PointLog）**: 积分余额（可负）与获取/消耗/回退。
- **会员等级规则（UserLevelRule）**: 成长值门槛与权益。
- **满减活动 / 档位（PromotionActivity / PromotionActivityLadder）**: 多档位、范围限定的满减。
- **风控规则 / 风控事件（RiskRule / RiskRecord）**: 拦截规则与命中留痕。
