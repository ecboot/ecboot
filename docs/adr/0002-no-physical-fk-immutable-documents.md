# 不建物理外键；交易单据与审计日志永不软删

我们决定全库不建物理 FOREIGN KEY：关联完整性由服务层同一本地事务保证，关联列一律建索引。理由：物理外键在高并发写入下扩大锁范围与死锁面，且是未来分库分表的最大结构障碍（跨库外键不可用）；换来的风险（应用缺陷导致孤儿数据）由"订单与订单项同事务写入"和对账任务兜底。

同一决策的另一半：**交易单据（订单/支付单/售后单/库存流水/回调日志）和审计日志不设 `deleted` 字段，永不删除**——取消是状态迁移不是删除；只有主数据（用户/商品/分类/品牌/模板/优惠券/后台账号）有软删除 `deleted` 标志。财务与合规要求交易凭证不可变、可追溯。

## Consequences

- 后台"删除商品"实际是下架+软删，历史订单凭 `trade_order_item` 快照自洽展示。
- 需要后台改数时走"调整"而非"删了重录"（如库存走 change_type=5 后台调整，留 `inventory_log` 痕迹）。
- 软删除与唯一索引的冲突采用"严格唯一"策略：软删用户的手机号仍占用，复用走后台改绑流程（避免 NULL 多值放行重复注册的漏洞）。**范围注记（V11 之后）**：本条适用于"普通软删除"；用户**注销**走匿名化流程（墓碑哈希方案，原手机号可重新注册），规则见 `docs/schema-design.md` § 注销匿名化——注销是合规动作而非普通软删，两者并存不矛盾。
