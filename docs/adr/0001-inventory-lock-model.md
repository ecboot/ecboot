# 库存采用"下单锁定"三段式，Redis 仅作前置挡板，DB 为唯一事实源

社交电商存在分享带来的瞬时流量尖峰，若采用"支付后扣库存"会出现支付成功却无货可发的资损与体验问题。我们决定库存采用**下单锁定制**：`inventory` 只存 `total` 与 `locked`（可售 = total − locked 为推导值，`CHECK(locked<=total)` 兜底），锁定/核销/释放/回补四种操作全部退化为单行原子条件 UPDATE（行锁串行化，不用乐观锁 version）。热点 SKU 竞争激烈时，在 DB 之前加 Redis Lua 预扣挡板——但 **Redis 只挡流量、可随时丢弃重建，任何时刻 DB 条件更新路径必须完整可用**；Redis 未命中或数值异常自动回退纯 DB，对账任务校验两侧偏差并重置。

## Considered Options

- 支付后扣库存（转化率友好，但超卖风险转移支付环节）——已拒绝。
- 乐观锁 version 字段 + 失败重试——单行热点下重试风暴反而劣化吞吐，条件 UPDATE 语义等价且更简单——已拒绝。
- 库存分桶（inventory 拆 bucket 维度摊薄行锁）——秒杀级再启用，属触发式演进。

## Consequences

- 取消/超时必须释放库存（Quartz 扫描 + 条件更新，天然幂等）；每次库存变更必须同事务写 `inventory_log`（前后值快照），这是对账与故障恢复的唯一依据。
